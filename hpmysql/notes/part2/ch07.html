Ch07 · Indexing for High Performance

Indexes are the single most powerful tool available for query performance — a well-designed index can eliminate millions of row reads; a missing or wrong index can turn a sub-millisecond query into a multi-second table scan.

B-Tree Index Internals

The dominant index structure in MySQL (InnoDB's B+Tree) organises sorted key values in a balanced tree where all data lives in the leaf nodes and all internal nodes are purely routing nodes. A search starts at the root page, follows one pointer per level down through branch pages, and arrives at a leaf page containing the target key alongside either the actual row data (clustered index) or a bookmark to the clustered index (secondary index).

Each page in InnoDB is 16 KB by default. A root or branch page holds hundreds to thousands of key-pointer pairs; a leaf page holds key-value pairs or key-row-data pairs. Because the tree is balanced, every search path has the same depth — typically 2–4 levels for tables up to hundreds of millions of rows. This makes point lookups and range scans predictable in cost. Crucially, leaf pages are doubly-linked in key order, so a range scan that finds the start point can then page-walk right without revisiting the tree.

B-Tree indexes support equality lookups, range scans, ORDER BY (if the index matches the sort key), and prefix matching on string columns. They do NOT support arbitrary substring searches (LIKE '%foo%' requires a full-text index or an external search engine) and do not accelerate predicates on the trailing columns of a composite index when a leading column has an unbound range.

Types of Indexes

MySQL supports four index types, each optimised for a different data access pattern.

B-Tree is the default and covers the vast majority of OLTP use cases: equality, range, prefix, and sort. InnoDB uses B+Tree (all data in leaves) rather than the pure B-Tree used in some academic texts.

Hash indexes are available in the MEMORY storage engine and as an adaptive structure inside InnoDB (Adaptive Hash Index, AHI). The AHI automatically builds in-memory hash entries for hot leaf pages — you cannot create a hash index explicitly in InnoDB. Hash indexes give O(1) equality lookups but cannot serve range scans, ORDER BY, or prefix matches.

Full-text indexes tokenise text content into an inverted index mapping each word to the list of documents containing it. Queries use MATCH() AGAINST() syntax. Full-text indexes in InnoDB support natural language mode, boolean mode (including proximity operators), and query expansion. They are not suitable for short token lookups (use B-Tree for exact column matches) and are eventually-consistent by default — changes are applied in the background.

Spatial (R-Tree) indexes partition two-dimensional geometric data using a minimum bounding rectangle hierarchy. ST_Within(), ST_Distance_Sphere() and similar spatial functions can utilise these indexes. They require GEOMETRY or POINT column types and a SPATIAL INDEX declaration.

Clustered vs Secondary Index

InnoDB organises every table as a clustered index — the primary key IS the table. The leaf pages of the primary key B+Tree contain the full row data in primary-key order. This is fundamentally different from MyISAM, where the data file is a heap and all indexes (including the primary key) are separate structures that point into the heap.

The consequence: primary key range scans in InnoDB are highly I/O efficient because related rows are physically co-located in sorted order. A scan of WHERE id BETWEEN 1000 AND 2000 reads a contiguous sequence of leaf pages. This is called clustering.

Secondary indexes do NOT store row data. Their leaf nodes contain the index key columns plus the primary key value (the "bookmark"). Querying a secondary index that does not cover all requested columns requires a bookmark lookup — a second B-Tree traversal into the clustered index for each matched row. This is the "double-tree" cost of secondary indexes.

The primary key choice matters immensely. A monotonically increasing integer PK (like an auto-increment) means new rows always append to the rightmost leaf page — minimal page splits. A UUID primary key distributes inserts randomly across all leaf pages, causing frequent page splits, high buffer pool fragmentation, and much worse sequential scan performance.

Covering Indexes

A covering index is any index whose leaf nodes contain all the columns needed to satisfy a query — so MySQL never needs to follow a bookmark back to the clustered index. This is the most impactful single index optimisation technique available. EXPLAIN shows Using index in the Extra column when a covering index is used.

Consider SELECT user_id, status, created_at FROM orders WHERE user_id = 42 AND status = 'paid'. A composite index on (user_id, status, created_at) covers this query completely: the leaf nodes contain all three requested columns, no row lookup needed. The query cost drops from O(matching_rows) random I/Os to O(1) tree traversal plus a short leaf scan.

Covering indexes are most valuable when the query matches many rows via the secondary index but those rows are spread throughout the clustered index. The classic example is a reporting query that filters on a non-primary-key column (e.g. status = 'pending') and retrieves a few additional columns. Without a covering index, each matched row causes a random I/O to the clustered index. With a covering index including those columns, the query reads only the (smaller) secondary index leaf pages sequentially.

Multicolumn Index Design

A composite (multicolumn) index on (a, b, c) is sorted first by a, then by b within each a value, then by c within each (a, b) pair. This physical ordering determines which predicates can use the index and how efficiently.

The leftmost prefix rule: the optimizer can use any leading prefix of the index columns. An index on (a, b, c) can serve queries filtering on a, on (a, b), or on (a, b, c). It cannot serve a query filtering only on b or only on c without also filtering on a.

The column ordering principle for composite indexes: equality predicates first, then range predicates, then sort columns. If a query is WHERE user_id = 42 AND created_at > '2024-01-01' ORDER BY created_at, the ideal index is (user_id, created_at) — the equality column first dramatically narrows the range, and created_at can serve both the range filter and the ORDER BY.

Selectivity is a secondary consideration for ordering equality columns among themselves. A highly selective column (one that eliminates most rows) should generally come first among the equality predicates. However, if multiple queries share the index and have different equality columns, sometimes a lower-selectivity column must come first to serve both queries. Index design is ultimately a workload analysis exercise, not just a mechanical rule application.

Index Maintenance

Indexes degrade over time through two primary mechanisms: fragmentation and stale statistics. Understanding both is essential for maintaining predictable query performance in production.

Fragmentation

When rows are inserted or updated in non-sequential primary key order, InnoDB must split leaf pages to maintain sorted order. A page split takes a full leaf page and moves half its entries to a newly allocated page, leaving both pages half-empty. Over time, a heavily-written table can have leaf pages that are only 50–70% full — this means more pages (more I/O) to scan the same number of rows. OPTIMIZE TABLE rebuilds the clustered index in sorted order, defragmenting the data. On InnoDB this is equivalent to ALTER TABLE ... ENGINE=InnoDB, which is an online operation in MySQL 8.0 using ALGORITHM=INPLACE.

Statistics and ANALYZE TABLE

The optimizer uses index statistics (cardinality estimates) to choose between available indexes and to estimate the cost of different join orders. InnoDB maintains these statistics via background sampling of leaf pages. After large bulk inserts, deletions, or data distribution shifts, statistics can become stale and cause the optimizer to choose suboptimal plans. Running ANALYZE TABLE tablename triggers a fresh statistics sample without locking. The innodb_stats_persistent system variable controls whether statistics are persisted across restarts (default: on in 5.6+). For tables with wildly non-uniform data distributions, innodb_stats_persistent_sample_pages can be increased to sample more leaf pages and produce more accurate estimates.

Index maintenance tasks to schedule: weekly ANALYZE TABLE on high-DML tables; monthly review of sys.schema_unused_indexes and sys.schema_redundant_indexes to prune indexes that cost writes but benefit no queries.
