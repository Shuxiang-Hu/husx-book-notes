Ch08 · Query Performance Optimization

A slow query is almost always doing too much work — reading rows it doesn't need, accessing columns it doesn't use, or forcing the server to materialise an intermediate result set it could have avoided. EXPLAIN is your microscope.

Why Are Queries Slow

Query response time is the sum of all time spent: waiting for a lock, waiting for I/O, CPU processing rows, sending bytes over the network. At any moment, a query is either executing (using resources) or waiting (blocked). The majority of production query performance problems fall into two categories of data access waste: fetching too many rows, and fetching too many columns.

Fetching Too Many Rows

The optimizer estimates how many rows must be examined to return the result. A ratio of rows_examined to rows_returned above 10:1 is a signal that the query is doing excessive work. Common causes: missing WHERE clause index, non-sargable predicate (e.g. WHERE YEAR(created_at) = 2024 prevents range scan use), or a JOIN ordering that starts with the large table instead of the selective one.

Fetching Too Many Columns

SELECT * is the most common culprit. Retrieving all columns forces MySQL to access the full clustered index row for every matched row, even when a covering index on the queried columns would have been sufficient. It also increases network transfer, increases serialisation cost at the application layer, and blocks covering-index optimisations. Always name the columns you need explicitly.

Other anti-patterns: using DISTINCT unnecessarily (forces deduplication of the entire result set), large LIMIT 1 OFFSET 100000 (must scan and discard 100 000 rows), and ORDER BY RAND() (materialises and sorts the full table).

EXPLAIN Anatomy

EXPLAIN (or EXPLAIN FORMAT=JSON / EXPLAIN ANALYZE in MySQL 8.0) describes the execution plan the optimizer chose. Reading EXPLAIN output fluently is the single most important query-tuning skill. Each row in EXPLAIN output represents one access operation in the query plan; complex JOINs and subqueries produce multiple rows.

The type column is the single most informative field. It describes the access method from most efficient to least. Understanding what each value means is a prerequisite for interpreting any EXPLAIN output.

Query Execution Pipeline

Understanding the lifecycle of a query from SQL string to result rows helps you diagnose problems at the right layer. Each stage has different failure modes and optimisation levers.

The parse stage tokenises the SQL string, checks syntax, and builds an abstract syntax tree. Parse errors surface here. Rewrite transforms the AST: correlated subqueries may be rewritten as joins, constant propagation simplifies predicates. Optimize is the most complex stage — it evaluates candidate execution plans using a cost model (I/O cost + CPU cost), considers available indexes, estimates row counts via statistics, and chooses the lowest-cost plan. The optimizer is cost-based but imperfect; it can make suboptimal choices when statistics are stale or the cost model underestimates random I/O.

Execute calls the storage engine API to fetch rows, applies WHERE filters that could not be pushed into the index (post-filter), sorts if necessary, and assembles the result set. Return streams rows back to the client — for large result sets, the client buffer matters. mysql_use_result() streams rows; mysql_store_result() buffers the entire result in client memory.

JOIN Algorithms

MySQL's join execution has evolved significantly. Understanding the available join algorithms helps diagnose why a particular multi-table query is slow and how to index or rewrite it.

In MySQL 8.0, the hash join replaces the old Block Nested Loop (BNL) algorithm for equi-joins that lack a usable index. The build phase constructs an in-memory hash table from the smaller table using join_buffer_size. If the hash table doesn't fit in memory, MySQL spills to disk using temporary files — a scenario to avoid. The probe phase scans the outer table, probing the hash table for each row. Unlike NLJ, hash join does not require indexes on the join columns, making it resilient to missing index configurations while still outperforming BNL.

Optimizer Limitations

MySQL's optimizer is sophisticated but has known limitations worth understanding so you can work around them.

UNION and Subquery Materialisation

UNION ALL appends result sets with no deduplication cost. UNION (without ALL) must deduplicate, which involves sorting or hashing the entire result — often expensive for large UNION arms. Correlated subqueries in WHERE clauses are re-evaluated once per outer row, even if the subquery result is constant. Rewriting as a JOIN or using a derived table (subquery in FROM clause) often produces a better plan.

No Parallel Query Execution

MySQL's InnoDB does not support intra-query parallelism (no parallel scan, no parallel hash join, no parallel sort). Each query executes single-threaded. For analytical workloads that need parallelism, consider MySQL HeatWave, ClickHouse, or an OLAP columnar store. The only MySQL-level parallelism available is at the connection level: multiple concurrent queries on separate connections.

Row-Locking Interaction

The optimizer does not account for lock contention when choosing plans. A plan that accesses rows in a different order from concurrent write transactions can cause deadlocks or increased lock wait time. Index range scans acquire gap locks in addition to row locks; full table scans escalate to a table-level intent lock. Sometimes adding an index not only speeds the query but also reduces locking scope, improving concurrency.

Optimizing Specific Patterns

COUNT Queries

COUNT(*) counts all rows including NULLs. COUNT(column) counts non-NULL values only — subtly different semantics. For InnoDB, COUNT(*) on a table without a WHERE clause requires a full index scan (there is no stored row count). For large tables, use the approximate information_schema.TABLES.TABLE_ROWS, or maintain a separate counter table updated transactionally.

GROUP BY and Aggregation

If the GROUP BY columns match a leading prefix of an available index, MySQL can produce the grouped result by walking the index in order — no sort or temporary table needed (Extra: Using index). Without such an index, MySQL must materialise the full result set into a temporary table and sort it — Extra: Using temporary; Using filesort — a potentially enormous cost for large tables.

LIMIT and OFFSET Pagination

Deep pagination with LIMIT 20 OFFSET 100000 is a well-known MySQL performance trap. MySQL must scan and discard 100 000 rows to reach the desired page. The solution is keyset pagination (also called cursor pagination): record the last-seen value of the sort key from the previous page and use it as a WHERE predicate: WHERE id > :last_id ORDER BY id LIMIT 20. This converts an O(offset) scan into an O(1) index seek regardless of page depth.

Covering Index Tricks

A covering index can be used as a deferred join target. Rather than fetching full rows from a wide table for a paginated query, first use a covering index to retrieve just the primary keys that match the predicate and pagination, then join back to the full table for those exact rows. This pattern is called a "late row lookup" or "deferred join":

SELECT * FROM orders
  JOIN (
    SELECT id FROM orders
    WHERE status = 'shipped'
    ORDER BY created_at DESC
    LIMIT 20 OFFSET 0
  ) AS ids USING (id);

The inner query uses a covering index on (status, created_at, id) to fetch 20 primary keys cheaply; the outer join then fetches the full row for only those 20 IDs via the clustered index.
