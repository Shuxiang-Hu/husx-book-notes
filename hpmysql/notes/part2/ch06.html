Ch06 · Schema Design and Management

Every byte you store has a cost: right data types eliminate wasted space, prevent type-coercion bugs, and make the optimizer's job tractable long before a single index is considered.

Choosing Optimal Data Types

MySQL is a statically typed storage engine. The column definition you choose at CREATE TABLE time influences on-disk row format, in-memory buffer-pool utilisation, sort buffer sizing, and whether a value must be converted before comparison with an indexed column. Three principles guide every decision: smallest type that can hold all real-world values, simplest type (integers beat strings for comparisons), and avoid NULL unless the absence of a value is semantically meaningful.

An INT column always occupies 4 bytes regardless of the numeric magnitude stored. A VARCHAR(255) column occupies only as many bytes as the actual string plus a 1- or 2-byte length prefix. TEXT and BLOB columns may spill to off-page storage, adding a pointer indirection that turns a single-row fetch into two I/O operations. DECIMAL stores digits as two 4-bit nibbles per digit — fully precise but significantly larger than FLOAT/DOUBLE for the same value range.

The type decision flowchart below summarises the canonical selection process. Start at the top and follow the first matching branch.

A common mistake is choosing VARCHAR(255) by default "to be safe." Wide VARCHAR columns bloat in-memory sort buffers — MySQL must allocate the full declared width when sorting, regardless of actual content. If your business logic genuinely caps a field at 32 characters, declare it VARCHAR(32).

Whole Numbers and Real Numbers

MySQL offers five integer widths. Always choose the smallest type that will never overflow. An INT UNSIGNED gives you 4.29 billion — sufficient for most internal IDs. When you need Snowflake-style distributed IDs or Unix nanosecond timestamps as IDs, reach for BIGINT UNSIGNED. Resist the temptation to use BIGINT everywhere: if every table's PK is 8 bytes instead of 4 bytes, secondary indexes — which embed the clustered index key as a bookmark — double that overhead per row, per secondary index.

For monetary values, FLOAT and DOUBLE are categorically wrong. Both use IEEE 754 binary floating-point, which cannot represent 0.1 exactly. After a few thousand arithmetic operations you accumulate rounding error that will not reconcile with paper statements. Use DECIMAL(19,4) for currency — 4 decimal places cover sub-cent precision, 15 integer digits cover values up to one trillion.

The UNSIGNED modifier doubles the positive range of any integer type by repurposing the sign bit. Use it for auto-increment primary keys — you get the positive range you actually need and gain a tiny storage win because the optimizer can sometimes use fewer comparisons. Be careful when mixing SIGNED and UNSIGNED columns in arithmetic: MySQL may silently cast and produce unexpected results.

String Types

The three string families — CHAR, VARCHAR, and TEXT/BLOB — differ in how MySQL stores them, where it stores them, and which operations can be applied efficiently.

CHAR(n) is right-padded to exactly n characters on disk and in memory. This makes equality comparisons branch-free and sort buffers exactly predictable. It is ideal for columns of fixed, known width: country codes (CHAR(2)), MD5 hashes (CHAR(32)), UUID strings (CHAR(36)).

VARCHAR(n) stores only the actual bytes used plus a 1-byte length prefix for values up to 255 bytes, or a 2-byte prefix beyond that. InnoDB stores VARCHAR inline in the page as long as the row fits. The max row size limit of 65 535 bytes applies across all VARCHAR columns combined — this trips up wide tables with many VARCHAR(255) columns.

TEXT / BLOB families store data off-page when they exceed the threshold (usually 768 bytes per column in the Antelope format, or when the row would overflow). Off-page storage means every access to that column fires an additional I/O to fetch the overflow page — a hidden performance tax for large values. You cannot use TEXT/BLOB columns as index keys (without a prefix index) and you cannot include them in a covering index.

One subtle gotcha: in utf8mb4, every character can consume up to 4 bytes. MySQL must allocate the maximum possible bytes for fixed-width operations like in-memory sorting. A VARCHAR(100) column in a utf8mb4 table requires 400 bytes of sort buffer allocation per row, not 100. This multiplier makes it even more important to declare realistic column widths.

JSON Data

MySQL 5.7 introduced a native JSON column type backed by an internal binary format (BJSON). Values are validated at write time and stored in a compact binary encoding that allows partial updates via JSON_SET() without rewriting the full document. Generated virtual columns over JSON paths can be indexed, giving you the flexibility of documents with the performance of a B-tree.

However, JSON columns are not a free pass. Every read of a JSON column deserialises the entire BJSON value — you cannot read one field without paying the cost of the whole document. There is no row-level partial locking inside a JSON field; an UPDATE on any path within the document locks the entire row. Foreign key constraints and JOINs require normalised relational columns.

The canonical guidance is: store structured data that you query by column value in normalised tables; use JSON for genuinely semi-structured, sparse, or user-extensible data where the shape varies across rows. Avoid the antipattern of stuffing everything into a single JSON column to avoid migrations — you lose all optimizer cardinality statistics on the fields within.

Schema Design Gotchas

Production schema problems tend to cluster around a small set of recurring antipatterns. Recognising them early — during design review rather than post-launch — saves enormous migration pain.

Too Many Columns

InnoDB stores rows in 16 KB pages. A table with 200 VARCHAR columns can push a single row past the 8126-byte inline threshold, forcing most columns off-page. Additionally, SELECT * across such a table transfers enormous amounts of unnecessary data across the network. MySQL's internal row parsing also becomes slower as column count grows. The limit is hard at 4096 columns, but performance degrades well before that.

ENUM Misuse

ENUM looks attractive: it stores values as a 1- or 2-byte integer internally while surfacing a human-readable string. The problem is that adding a new valid value requires an ALTER TABLE, which is a blocking operation on older MySQL versions and an online DDL operation in 8.0+ but still risks production impact. More critically, the set of valid values is embedded in the column definition — not in an application-level lookup table where it can be queried and extended without schema changes. Use TINYINT + a lookup table, or VARCHAR if the domain is truly open-ended.

NULL Abuse

NULL has well-defined semantics — "unknown" or "not applicable" — but is frequently misused as a sentinel for "not yet set," "zero," or "empty string." Problems arise because: NULL propagates through arithmetic (1 + NULL = NULL), comparisons require IS NULL not = NULL, and MyISAM/InnoDB must store a null-bitmap per row even when a column is rarely null. Wherever a column has a sensible default, declare it NOT NULL DEFAULT '' or NOT NULL DEFAULT 0. Reserve NULL for genuinely unknown values.

Entity-Attribute-Value (EAV) schemas deserve special mention. An EAV table stores all attributes as rows in a generic (entity_id, attribute_name, attribute_value) table, circumventing schema evolution costs. The query cost is enormous: retrieving a single "row" requires pivoting dozens of rows from the EAV table. The optimizer has no column statistics on attribute values. Indexed lookups on values require full scans or at best a range scan on the value column with poor selectivity. EAV is almost always the wrong answer for a relational database.

Schema Management and Migrations

Altering a large table in production MySQL is one of the most nerve-wracking DBA operations. A naïve ALTER TABLE on a 500 GB table can lock the table for hours. MySQL 8.0 supports online DDL for many operation types via ALGORITHM=INPLACE, LOCK=NONE, but not all operations qualify, and even online DDL consumes I/O that impacts query latency.

Two open-source tools have become the de facto standard for zero-downtime schema changes in MySQL production environments: gh-ost (GitHub's Online Schema Transformation) and pt-online-schema-change (Percona Toolkit).

gh-ost Pipeline

gh-ost works by connecting to MySQL as a replication client. It creates a shadow table (_tablename_gho), copies rows in batches, and simultaneously tails the binary log to apply concurrent DML changes to the shadow table. When the shadow table catches up, gh-ost performs a brief atomic rename. Because it uses the binlog rather than triggers, it imposes lower write amplification than pt-osc. It also exposes a Unix socket for real-time throttle control without restarting the migration.

For migration safety, always test on a staging environment first, measure row-copy throughput against your peak DML rate, and configure --max-load thresholds to pause the copy when the server comes under write pressure. With gh-ost's socket interface you can even hook the migration into your CI/CD pipeline and automatically pause during deployments or traffic spikes.
