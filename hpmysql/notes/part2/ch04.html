Ch04 · Operating System and Hardware Optimization

MySQL performance is ultimately constrained by the hardware stack beneath it — the interaction between CPU topology, memory capacity, and storage characteristics determines the ceiling for every configuration knob above it.

What Limits MySQL Performance

MySQL performance bottlenecks form a stack. At the top, application-level issues (bad SQL, poor connection management) are the most common and cheapest to fix. Beneath those sit network bottlenecks (high latency between app and DB), then disk I/O (the traditional MySQL bottleneck on spinning disks), then CPU (becomes the bottleneck when everything fits in the buffer pool), and finally memory (determines whether working set fits in cache). Correctly identifying which layer is the actual bottleneck before tuning is the most important skill a DBA can develop.

A common failure mode is premature hardware investment: purchasing larger servers before diagnosing whether the problem is actually a missing index or a lock contention issue. The authors recommend the following diagnostic order: (1) check SHOW PROCESSLIST for lock waits or long-running queries; (2) check P_S statement digest for full-scan patterns; (3) check OS tools (vmstat, iostat, top) for resource saturation; only then consider hardware changes.

CPU Selection

MySQL's query processing is largely single-threaded per query — the optimizer and executor run sequentially within one connection thread. This means MySQL benefits more from fast single-core speed (high clock frequency, large per-core L3 cache) than from a large number of cores. A 32-core server with 2.4 GHz cores will often perform worse for OLTP than a 16-core server with 3.8 GHz cores at the same price point, because each connection is still waiting for its single thread to complete.

The exception is high-concurrency workloads where many queries run simultaneously: here core count matters for parallel execution of different connections. But even then, InnoDB's internal mutex architecture limits how effectively MySQL scales beyond about 32 active threads before contention dominates.

NUMA Topology

Modern multi-socket servers use Non-Uniform Memory Access (NUMA) architecture: each CPU socket has its own local memory bank and can access remote sockets' memory only via the inter-connect (QPI/UPI). Remote memory access is roughly 1.5–2× slower than local. MySQL's buffer pool, if allocated across NUMA boundaries, can suffer from this penalty on every page access. The recommended setting is innodb_numa_interleave=ON, which distributes buffer pool pages evenly across NUMA nodes using the Linux memory policy MPOL_INTERLEAVE, avoiding hot-spot contention on a single node.

Memory and Disk

The relationship between memory and disk is simple in principle: if MySQL's entire working set — the pages actively accessed by current workloads — fits in the InnoDB buffer pool, disk I/O drops near zero and the server is effectively CPU-bound. Every dollar spent on RAM to keep the working set in memory is among the highest-leverage investments in MySQL performance.

In practice, the working set is smaller than the full dataset. A typical web application has a strong temporal locality pattern: a small fraction of "hot" rows accounts for the majority of reads. The classic guideline is that a buffer pool equal to 20–30% of the total data size often captures 95%+ of reads. Profile Innodb_buffer_pool_reads vs Innodb_buffer_pool_read_requests to measure your actual hit rate.

For disk, the dominant metric is random I/O latency and IOPS, not sequential bandwidth. Random 4 KB reads and writes (the size of MySQL's default page size) are the workload that matters. This is why SSDs transformed MySQL performance: an NVMe SSD delivers 100–500 µs random read latency vs 4–10 ms for a spinning disk — a 20–40× improvement that directly translates to query latency.

Solid-State Storage

Not all flash storage is equivalent. Consumer SATA SSDs, enterprise SATA SSDs, enterprise SAS SSDs, PCIe NVMe SSDs, and cloud-managed block storage (like AWS EBS gp3) have dramatically different latency and IOPS profiles. For MySQL production use, the authors recommend NVMe or equivalent because the bottleneck under write-heavy InnoDB workloads moves to the redo log fsync path — where sub-100 µs write latency matters enormously.

Write amplification is a critical concern with SSDs. InnoDB's doublewrite buffer was designed for HDD (to protect against torn writes during partial page writes at crash time). On SSDs with atomic write guarantees (like some NVMe drives), the doublewrite buffer is unnecessary overhead and can be disabled with innodb_doublewrite=OFF, but only after verifying your SSD provides atomic sector writes.

RAID

RAID (Redundant Array of Independent Disks) is less relevant for cloud deployments, where storage redundancy is managed by the cloud provider, but remains important for on-premises and some bare-metal cloud configurations. The key question for MySQL is how RAID affects write latency (critical for the redo log fsync path) and read throughput (important for buffer pool warmup after restart).

RAID 10 (stripe of mirrors) is the standard recommendation for MySQL data directories: it provides both good write performance (no parity calculation overhead) and fault tolerance (survives one disk failure per mirror pair). Avoid RAID 5 for MySQL — the read-modify-write parity cycle on random writes creates significant latency on the InnoDB redo log path, and the performance degradation during a rebuild is severe.

With SSDs and NVMe, hardware RAID controllers can actually become a bottleneck due to the RAID card's cache and protocol overhead being slower than the drives themselves. Many modern deployments skip hardware RAID entirely and rely on OS-level replication (LVM mirroring, software RAID 1) or application-level redundancy (MySQL replication).

Filesystem and Kernel Tuning

Linux filesystem and kernel settings have a significant impact on MySQL I/O performance. The three highest-impact areas are: filesystem type, I/O scheduler, and power management.

Filesystem

XFS is the recommended filesystem for MySQL data directories on Linux. It handles the InnoDB workload (many small random writes, large sequential redo log writes) better than ext4 at high I/O rates, with better metadata performance and fewer fragmentation issues at large file sizes. The noatime,nodiratime mount options eliminate unnecessary inode updates on every read, which is a measurable overhead for MySQL's many small random reads.

I/O Scheduler

For NVMe and SSDs, use the none or mq-deadline scheduler (depending on kernel version). The cfq (Completely Fair Queuing) scheduler was designed for spinning disks and introduces unnecessary latency for SSDs by reordering I/O requests that don't benefit from seek minimization. For spinning disks, deadline or mq-deadline prevents request starvation better than cfq.

Power Management

CPU frequency scaling (cpufreq) governs with ondemand or powersave policies can dramatically reduce MySQL throughput by scaling down CPU frequency under moderate load. The performance governor runs CPUs at maximum frequency constantly. On dedicated MySQL hosts, always set performance governor or disable frequency scaling via BIOS.
