Ch05 · Optimizing Server Settings

InnoDB configuration is the highest-leverage tuning surface in MySQL — a handful of variables governing the buffer pool, redo log, and I/O subsystem determine the performance ceiling for all workloads running above them.

How MySQL Configuration Works

MySQL variables exist in a three-level scope hierarchy. Global variables apply to the server instance as a whole — changes take effect for new connections (and sometimes immediately). Session variables can be overridden per connection and revert to the global default when the session ends. A handful of variables are set at statement execution time. Understanding this scope model prevents the common mistake of tuning a session variable in one connection and wondering why performance doesn't improve server-wide.

Configuration sources are evaluated in priority order: command-line arguments override configuration file values, which override compiled-in defaults. The my.cnf (or my.ini on Windows) file is processed in a fixed section order: [mysqld_safe], then [mysqld]. On MySQL 8.0, the SET PERSIST command writes a variable to mysqld-auto.cnf in the data directory, which is applied after my.cnf — use this for runtime tuning that survives restarts without editing configuration files.

The authors' approach to configuration: start with the minimum viable set (buffer pool size, redo log size, innodb_flush_method), measure under production load, then tune incrementally. Cargo-culting a 200-line my.cnf from the internet is a reliable way to make things worse.

InnoDB Buffer Pool

The buffer pool is the single most important configuration in MySQL. It is a shared memory pool of 16 KB pages that caches data and index pages from InnoDB tablespaces. When a query needs a page, InnoDB first checks the buffer pool — a hit costs nothing beyond a mutex acquisition; a miss triggers a synchronous disk read and the page is loaded into the pool.

On a dedicated MySQL server, set innodb_buffer_pool_size to 70–80% of available physical RAM. Leave headroom for the OS page cache, per-thread buffers (sort_buffer, join_buffer, tmp_table), and MySQL's own overhead. A 128 GB server should have roughly 96–100 GB allocated to the buffer pool. In MySQL 8.0, the buffer pool can be resized online without restart via SET GLOBAL innodb_buffer_pool_size = N, though the resize is asynchronous and may take time on large pools.

Multiple buffer pool instances (innodb_buffer_pool_instances) reduce mutex contention on multi-core servers. The pool is partitioned into instances and pages are assigned to instances by page hash. The default of 8 instances is appropriate for most servers; increase to 16 for very high-concurrency workloads.

LRU List Structure

The buffer pool uses a modified LRU (Least Recently Used) algorithm with a midpoint insertion strategy. The LRU list is logically divided into a "young" (hot) half and an "old" (cold) half. New pages enter at the midpoint — the boundary between the two halves — rather than the head of the list. This prevents large sequential scans (which would evict the entire hot half in a naive LRU) from polluting the pool. A page is promoted to the hot half only after being accessed again while still in the cold half.

The flush list tracks dirty pages (modified but not yet written to disk) in order of their oldest modification LSN. The background flush thread writes dirty pages to disk in LSN order to maintain a valid checkpoint. The free list holds unallocated pages available for immediate use.

InnoDB Redo Log

The redo log (write-ahead log) is InnoDB's durability mechanism. Before modifying any buffer pool page, InnoDB writes a compact redo log record describing the change. After the redo log record is durably written to disk (an fsync), the transaction can be considered committed, even if the corresponding data page is still dirty in the buffer pool. On crash recovery, InnoDB replays the redo log forward from the last checkpoint to reconstruct all changes.

The redo log is a fixed-size circular file (or set of files). In MySQL 8.0, the redo log size is controlled by innodb_redo_log_capacity (replacing the old innodb_log_file_size × innodb_log_files_in_group). A larger redo log allows more dirty pages to be resident in the buffer pool between checkpoints, reducing I/O write amplification. A smaller redo log forces more frequent checkpoints and more disk writes, but reduces crash recovery time.

The critical constraint is the checkpoint LSN: InnoDB cannot overwrite the redo log ring buffer beyond the oldest dirty page's LSN. If the write position catches up to the checkpoint, InnoDB must synchronously flush dirty pages — a furious flushing event that causes severe write latency spikes. The target is to size the redo log such that the write position and checkpoint stay comfortably apart. The rule of thumb: redo log capacity should be at least 1 hour of redo log generation at peak write throughput.

InnoDB Tablespace

InnoDB stores table data in tablespaces — logical containers that map to one or more files on disk. MySQL 5.6 introduced innodb_file_per_table=ON (the modern default), giving each table its own .ibd file. This mode enables online table operations like ALTER TABLE … ALGORITHM=INPLACE and makes it easy to reclaim disk space by dropping tables. The original shared tablespace model (all tables in ibdata1) is still used for the InnoDB system tables, undo logs (in older versions), and the data dictionary.

MySQL 8.0 further separates undo logs into dedicated undo tablespace files (undo_001, undo_002 by default), allowing the undo tablespace to be purged and truncated independently. This is important for workloads with long-running transactions that accumulate large undo histories.

I/O Configuration

InnoDB's I/O subsystem has several layers of configuration that interact with each other and with the underlying OS and filesystem. Getting these right is the difference between a MySQL server that saturates its storage and one that leaves I/O bandwidth on the table.

innodb_flush_method

This variable controls how InnoDB issues writes to disk. The most important options are:

  • O_DIRECT — Bypasses the OS page cache for data file reads and writes. Prevents double-buffering (data cached in both the buffer pool and the OS cache), the correct setting for a dedicated MySQL server with a large buffer pool. Required for accurate memory utilization — without it, the OS cache can silently consume RAM you thought was free.
  • O_DIRECT_NO_FSYNC — Like O_DIRECT but skips the fsync on flushed pages. Safe on some filesystems (XFS, ext4 with journal) that provide write ordering guarantees. Can improve performance but requires validation.
  • fsync (default) — Uses the OS page cache for reads and writes, then calls fsync() to flush. Correct for virtual machines where O_DIRECT may have issues with virtual disk drivers.

Doublewrite Buffer

The doublewrite buffer protects against torn page writes — partial writes of a 16 KB InnoDB page that can occur if the system crashes mid-write on storage that writes in smaller atomic units than 16 KB. InnoDB writes pages to the doublewrite buffer area first, then to their actual tablespace location. On crash recovery, if a data page looks corrupt, InnoDB recovers the intact copy from the doublewrite buffer. On storage that guarantees atomic writes of 16 KB or larger (some NVMe drives, AWS io2), the doublewrite buffer can be disabled with innodb_doublewrite=OFF for a ~5–10% write performance gain.

Concurrency Settings

MySQL concurrency is governed by two distinct subsystems: the thread cache (connection-level) and InnoDB thread concurrency (storage engine-level). Getting both right prevents two common failure modes: connection storm (too many OS threads waiting for CPU) and InnoDB concurrency bottleneck (threads serializing inside the storage engine).

Thread Cache and max_connections

max_connections is the ceiling on simultaneous connected clients. Each connection consumes approximately 1–2 MB of RAM for its thread stack plus per-thread buffers. On a 128 GB server, 1000 connections consumes roughly 2 GB in thread overhead alone — before counting sort buffers or join buffers that may be allocated during query execution. The key insight: max_connections should be set based on what the server can actually serve concurrently, not as a high-water mark to allow growth. If 1000 connections are all active simultaneously, MySQL will likely be CPU-saturated long before memory is an issue.

thread_cache_size controls how many idle threads are kept in a cache pool for reuse by new connections. Without this, every new connection requires an OS-level thread creation, which can add 1–5 ms of connection overhead. Set to roughly max_connections / 10 — this is usually enough to absorb connection bursts without excess memory consumption.

InnoDB Thread Concurrency

innodb_thread_concurrency limits how many threads can be executing inside InnoDB simultaneously. When this limit is reached, additional threads must wait in a queue (the ticket system). The correct value depends on CPU cores and workload. A common starting point is 2 × CPU cores. Setting it to 0 (the default) disables the limit entirely, which can lead to excessive context switching on heavily loaded servers. The goal is to keep all CPU cores utilized without them fighting for InnoDB's internal mutexes.
