Ch09 · Replication

MySQL replication is the foundation of high availability, disaster recovery, and read scaling — understanding the mechanics from binlog to relay log to apply thread is prerequisite knowledge for every production DBA.

How Replication Works

MySQL replication is asynchronous by default. The source server writes every committed change to a binary log (binlog). The replica connects to the source with a dedicated I/O thread, reads binlog events from the source's binlog dump thread, and writes them to the replica's own relay log. A separate SQL thread (or multiple parallel apply threads in MySQL 8.0+) reads events from the relay log and applies them to the replica's data files. This three-thread model decouples network transfer from apply latency and lets the replica buffer events during apply slowdowns.

Semi-synchronous replication (rpl_semi_sync plugin) modifies this model: the source waits for at least one replica to acknowledge receipt into its relay log before returning success to the client. This prevents data loss on source crash at the cost of slightly higher write latency. It does NOT wait for the replica to apply the event — only to receive it.

Replication position tracking is managed via binlog coordinates (file name + offset) in classic replication, or globally unique transaction IDs (GTIDs) in GTID-based replication. GTID mode simplifies failover automation because any replica can be promoted to source without needing to calculate equivalent binlog coordinates across servers.

Replication Formats

The binary log can record changes in three formats, controlled by the binlog_format system variable. The choice has significant implications for consistency, safety, and replicated data fidelity.

Statement-Based Replication (SBR) logs the exact SQL statement executed on the source. The replica re-executes the statement. This produces compact binlog events but is unsafe for non-deterministic statements: NOW(), UUID(), RAND(), or any function whose result depends on server state that may differ between source and replica. SBR also requires statement execution context (session variables) to be replicated alongside the SQL.

Row-Based Replication (RBR) logs the actual before/after images of every changed row. The replica applies the row changes directly, bypassing re-execution. RBR is always safe regardless of non-determinism, but produces larger binlog events — a multi-row UPDATE that affects 1 million rows logs 1 million row change events. RBR is the recommended default in MySQL 5.7+ and 8.0.

Mixed-mode uses SBR by default but automatically switches to RBR when a non-deterministic statement is detected. In practice, the mix of formats makes it harder to debug and reason about replication state; most production environments choose pure RBR.

GTID Replication

Global Transaction Identifiers (GTIDs) give every committed transaction a globally unique ID composed of the originating server's UUID and a monotonically increasing sequence number: 3E11FA47-71CA-11E1-9E33-C80AA9429562:23. This identifier is written into the binlog and replicated along with the transaction data.

Each MySQL server maintains a gtid_executed set — the set of all GTIDs it has applied. When a replica connects to a new source, it sends its gtid_executed set; the source automatically sends only the transactions the replica hasn't applied yet. This makes failover dramatically simpler: pointing a replica at a new source is safe regardless of binlog file coordinates.

GTID-based replication requires gtid_mode=ON and enforce_gtid_consistency=ON. Some SQL patterns are incompatible with GTID consistency enforcement: non-transactional DML inside transactions, CREATE TABLE ... SELECT, and temporary tables within transactions. These must be refactored before enabling GTID mode in a running cluster.

Replication Topologies

MySQL replication supports several topologies, each with different trade-offs for read/write distribution, high availability, and operational complexity.

Topology Reads / Writes HA Characteristics Complexity Best Use Case
Active/Passive All traffic to source; replica idle Manual or orchestrated failover; seconds to minutes Low Disaster recovery warm standby
Active/Read Pool Writes to source; reads distributed across replicas Replica lag possible; failover needs promotion Medium Read-heavy OLTP, reporting offload
Chain (cascading) Writes to source; reads anywhere Increased lag at each hop; more SPOF Medium Reduce source binlog dump threads
Multi-Source One replica applies from multiple sources Complex; no standard failover High Data warehouse aggregation, cross-shard queries
Group Replication Single-primary: writes to primary only; multi-primary: any node Automatic failover via Paxos (<30 s) High Zero-downtime HA; InnoDB Cluster

Monitoring Replication

Replication lag is the most critical replication health metric. Lag means the replica is serving stale data — a business problem if reads that must be consistent are routed to the replica. Two methods exist for measuring lag, and they give different answers.

Seconds_Behind_Master (shown by SHOW REPLICA STATUS) measures the timestamp difference between the event currently being applied by the SQL thread and the current wall clock time on the replica. This is an estimate based on event timestamps in the relay log. It can be misleading: it reports 0 when the SQL thread is idle (caught up) but the I/O thread may be behind; it can jump suddenly; and it doesn't account for multi-source scenarios.

Heartbeat-based lag is more accurate. A separate process writes a timestamp to a known table on the source every N seconds. The replica reads that timestamp and computes NOW() - heartbeat_timestamp as the true perceived lag. Tools like Percona Toolkit's pt-heartbeat implement this pattern. This measures actual data propagation delay, not relay-log metadata.

Key replication monitoring queries to run regularly:

  • SHOW REPLICA STATUS\G — comprehensive status including SQL/IO thread state, relay log position, lag estimate
  • SELECT * FROM performance_schema.replication_connection_status — I/O thread detail in 8.0
  • SELECT * FROM performance_schema.replication_applier_status_by_worker — per-worker parallel apply status

Common Problems and Solutions

Stale Reads

An application reads from a replica immediately after writing to the source. The replica hasn't applied the change yet, so the read returns stale data. Solutions: route reads to the source for sessions that just wrote (read-your-writes consistency); use a ProxySQL rule to send transactions to the primary; implement application-level replica lag awareness with a fallback to the source when lag exceeds a threshold.

Split-Brain

In a manual failover scenario, if the original source comes back online after the replica has been promoted, two nodes may accept writes simultaneously. Protecting against split-brain requires fencing: STONITH (Shoot The Other Node In The Head) via IPMI/iDRAC power fence, or VIP/DNS TTL expiration before the old source can be reached. Orchestrator (GitHub's replication manager) implements anti-split-brain checks before promoting a replica.

Non-Unique Server IDs

Every MySQL instance in a replication topology must have a unique server_id. Cloned VMs or container replicas often inherit the same server ID as the source, causing replication loops or silent dropped events. Always set server_id explicitly in /etc/mysql/my.cnf using a value derived from IP octet, hostname hash, or configuration management tool.

Large Transaction Lag Spikes

A single large transaction (e.g., batch delete of 5 million rows) executes as one atomic RBR event on the replica's SQL thread. Since MySQL 5.7, parallel replication (slave_parallel_workers > 0, slave_parallel_type=LOGICAL_CLOCK) can apply independent transactions concurrently. However, a single large transaction still serialises the apply thread. The solution is to batch large operations into smaller transactions on the source.
