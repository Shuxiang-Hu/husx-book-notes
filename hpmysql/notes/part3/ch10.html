Ch10 · Backup and Recovery

A backup you have never tested restoring is not a backup — it is a false sense of security. Recovery planning starts with defining RTO and RPO, then working backwards to the backup strategy that satisfies them.

Why Backups and Recovery Planning

Two metrics define a recovery strategy. Recovery Time Objective (RTO) is the maximum acceptable downtime: how long can the business tolerate the system being unavailable? Recovery Point Objective (RPO) is the maximum acceptable data loss: how much data can be lost without causing unacceptable business harm? A financial transaction system might demand RTO < 1 minute and RPO = 0 (no data loss). A content platform might accept RTO < 4 hours and RPO < 1 hour.

RTO and RPO are inversely related to backup cost. Near-zero RPO requires continuous replication or binlog streaming. Near-zero RTO requires a warm standby that can be promoted in seconds. Both together require replication with semi-synchronous or synchronous mode — expensive in latency and infrastructure cost. The RTO/RPO matrix helps articulate these trade-offs to the business.

Recovery planning must include documented runbooks for each failure scenario: single-table accidental DROP, replica lag emergency, source host failure, datacenter outage. Runbooks should be tested under realistic conditions at least quarterly. "Chaos Day" fire drills — deliberately failing a source in a staging environment and executing the runbook — reveal gaps in tooling, permissions, and documentation before a real incident.

Backup Types

MySQL backup strategies can be characterised along two independent axes: logical vs physical and online vs offline. These produce four combinations, each with distinct trade-offs.

Logical backups export data as SQL statements or delimited text. They are portable across MySQL versions and storage engines, and individual tables can be restored without restoring the entire dataset. The trade-off is that export and import are CPU-intensive and slow for large datasets — a 500 GB logical backup may take hours to restore.

Physical backups copy the raw InnoDB data files and redo logs. They are much faster to restore (file copy rather than SQL replay) and are byte-for-byte copies of the tablespace. The trade-off is version sensitivity — restoring across major MySQL versions requires intermediate upgrade steps — and less granular restore capability.

Online (hot) backups can run while MySQL serves traffic. InnoDB's MVCC allows consistent reads without stopping writes. Hot backups are production-safe. Offline (cold) backups require stopping MySQL or acquiring a global read lock, causing downtime. Cold backups are rarely used for production OLTP tables but are common for archival or migration scenarios.

Full vs incremental is a third dimension. A full backup copies all data. An incremental backup captures only changes since the last full (or last incremental). XtraBackup supports incremental backups by tracking the LSN (Log Sequence Number) watermark — only pages modified since the last backup are copied. Incrementals reduce backup duration and storage, at the cost of a more complex restore chain (full + all incrementals must be applied in sequence).

Percona XtraBackup Internals

XtraBackup achieves a consistent hot backup without locking by exploiting InnoDB's redo log. The backup proceeds in two concurrent phases.

Copy phase: XtraBackup copies InnoDB data files (*.ibd, ibdata1) to the backup directory. Because MySQL is live, these files are being modified by ongoing transactions. The copies may contain incomplete transactions or torn pages — they are not yet consistent.

Redo log tail copy: Simultaneously, a background thread continuously copies the InnoDB redo log (the WAL) from the moment the copy phase starts. The redo log records all changes, so by capturing the tail continuously, XtraBackup can later replay all changes that occurred during the copy phase.

Prepare phase (run offline after copy): XtraBackup replays the captured redo log tail against the copied data files, bringing them to a consistent crash-recovery state — identical to what InnoDB does on startup after an unclean shutdown. The result is a consistent, point-in-time snapshot of the database.

For very large databases, XtraBackup supports streaming to a remote host over SSH or to object storage via compression pipelines: xtrabackup --backup --stream=xbstream | gzip | aws s3 cp - s3://bucket/backup.xbstream.gz. The --parallel flag controls the number of file-copy threads; --compress and --encrypt add on-the-fly compression and AES encryption. Incremental backups use --incremental-basedir pointing to the previous backup, copying only pages with LSN greater than the base backup's LSN.

Point-in-Time Recovery

Point-in-time recovery (PITR) restores the database to any specific moment in time — not just the most recent backup. It combines a base physical backup with subsequent binary log replay. This is the critical capability for recovering from accidental data deletion or corruption where "restore to last backup" would lose too much work.

PITR requires that binary logs are retained from the time of the base backup. The binlog retention policy (binlog_expire_logs_seconds in MySQL 8.0, or expire_logs_days in 5.7) must be set to cover at least the time between full backups plus your recovery window. Streaming binary logs to S3 or GCS in near-real-time (using MySQL's binlog dump protocol or tools like Binlog Server) ensures that even if the source server's disk fails, you still have the binlogs.

The mysqlbinlog command is the tool for extracting SQL from binary logs. Key flags: --start-datetime / --stop-datetime for time-based filtering, --start-position / --stop-position for position-based filtering, and --database to filter events for a specific database. For row-based binlogs, the -v flag adds human-readable row comments to the decoded event output.

Backup Validation Pipeline

A backup that cannot be restored is worthless. The only way to know that a backup is restorable is to restore it. Automated backup validation should be a first-class part of any backup strategy.

The smoke test phase should include: row count comparison against the source (within expected tolerance for lag), a sample query on each critical table, and verification that the gtid_executed set is consistent with the expected backup timestamp. Automate this entire pipeline via a weekly cron or CI job. Failures should page the on-call DBA immediately, not be silently logged.

Backup Tools Overview

Four tools cover the majority of MySQL backup workloads. Understanding their capabilities and limitations is essential for choosing the right tool for each situation.

mysqldump is the oldest and most universally available logical backup tool. It uses --single-transaction to start a consistent read transaction (InnoDB MVCC) before dumping, allowing a hot backup without locking for InnoDB tables. MyISAM tables require --lock-all-tables. Output is plain SQL. Restore speed is limited by sequential SQL replay — typically 50–200 MB/s effective throughput on a modern server.

mydumper is a parallel logical backup tool. It uses multiple threads to dump tables concurrently, dramatically reducing backup duration for large databases. It also supports parallel restore via myloader. Backup and restore are 3–10x faster than single-threaded mysqldump for large databases. Output format is per-table SQL files, easier to restore individual tables selectively.

Percona XtraBackup is the standard for large InnoDB production backups. Hot backup, fast restore (file copy), incremental support, encryption, and streaming to object storage. Free, open-source. The recommended tool for databases where restore time matters.

MySQL Enterprise Backup (MEB) is Oracle's commercial equivalent to XtraBackup. It supports additional features like partial backups (specific tables only), transportable tablespaces, and cloud storage integration. Requires a MySQL Enterprise subscription.
