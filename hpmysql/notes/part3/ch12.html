Ch12 · MySQL in the Cloud

Cloud MySQL deployments span a wide spectrum from fully managed services that abstract away the OS entirely to self-hosted instances on VMs where every kernel parameter is yours to tune — each point on that spectrum involves genuine trade-offs between operational control and engineering leverage.

Managed vs Self-Hosted Trade-offs

The fundamental choice when deploying MySQL in a cloud environment is how much of the operational stack you want to own. Self-hosted MySQL on a cloud VM gives you complete control: you choose the OS, compile MySQL from source if you wish, configure every InnoDB parameter, manage your own HA with Orchestrator or MHA, and build custom backup pipelines. In exchange you carry the full operational burden — patching, failover automation, replication monitoring, capacity planning, and upgrade management all fall to your team.

Managed database services — Amazon RDS, Amazon Aurora, Google Cloud SQL, Azure Database for MySQL — handle OS patching, storage provisioning, automated backups, and often automated failover. The service SLA backs availability; you pay a markup over raw compute cost for the abstraction. The tradeoff is reduced visibility: you cannot access the OS, cannot tune OS-level parameters like transparent_huge_pages or NUMA interleaving, and are constrained to the MySQL versions and configuration parameters the provider exposes via a parameter group API.

The chapter's key insight is that the managed vs self-hosted decision should be made per-workload, not per-company. A reporting database with moderate traffic and no unusual tuning requirements is an excellent candidate for a managed service. A latency-critical OLTP cluster at 100 k+ TPS with custom InnoDB patches may require self-hosted VMs to extract every microsecond of performance.

Amazon Aurora for MySQL

Amazon Aurora is not simply RDS with a better SLA — it is a fundamentally different storage architecture. Aurora decouples compute (the MySQL-compatible server process) from storage (a proprietary distributed log-structured storage service). The storage layer spans 6 copies of your data across 3 Availability Zones: 2 copies per AZ. Writes are acknowledged once 4 of 6 copies have durably received the redo log record. Reads require only 3 of 6 copies to be available. This quorum design tolerates an entire AZ outage for both reads and writes, and tolerates 2-copy failures for writes.

Because Aurora storage is a distributed log, Aurora does not write the double-write buffer that InnoDB normally uses on local disk to prevent partial page writes. The log-structured storage makes partial writes impossible by construction. Aurora can therefore achieve higher write throughput than standard InnoDB on equivalent compute because the critical write path is shorter: only redo log records flow over the network to the storage service, not full pages. Aurora measures this as "log record writes" vs the full page writes of standard InnoDB.

Aurora supports up to 15 read replicas, all sharing the same underlying storage. Unlike standard MySQL asynchronous replication where replicas re-execute binlog events, Aurora replicas simply apply redo log records from the shared storage. Replica lag is typically under 10–20 milliseconds rather than the seconds-to-minutes range common with MySQL async replication under write pressure.

Aurora failover is substantially faster than RDS Multi-AZ: typically 15–30 seconds for a promotion to complete, because no data needs to be replicated to the new primary — it already shares the same storage. The book notes that Aurora is not the right choice for every workload: its proprietary storage engine means that migrating away from Aurora is more complex than migrating between standard MySQL instances, and the per-IO pricing model can be surprisingly expensive for high-IOPS workloads compared to provisioned IOPS on standard RDS.

GCP Cloud SQL

Google Cloud SQL for MySQL is a fully managed relational database service built on standard MySQL (not a custom storage engine). Cloud SQL manages instance provisioning, storage auto-resize, automated backups, point-in-time recovery via binary log replay, and OS/engine patching. Unlike Aurora, Cloud SQL uses standard MySQL replication under the hood — a standby replica receives binlog events from the primary and applies them asynchronously, then a managed failover mechanism promotes the standby when the primary becomes unavailable.

The key Cloud SQL HA mechanism is the regional instance configuration: the primary and the standby are placed in different zones within the same region, connected by a synchronous replication mechanism for the write-ahead log. Cloud SQL uses a combination of disk-level replication and MySQL binlog to ensure the standby is always within one transaction of the primary. Failover is automated and typically completes in 60–120 seconds, which is slower than Aurora but acceptable for most workloads.

Cloud SQL Proxy is the recommended connection method: it provides IAM-based authentication, automatic TLS, and eliminates the need to whitelist IP addresses. The proxy runs as a sidecar on the application host (or as a Kubernetes sidecar container) and forwards connections to the Cloud SQL instance over a secure channel authenticated with a service account. This is particularly important in containerized environments where IP addresses are ephemeral.

MySQL on Virtual Machines

When a managed service is insufficient — due to compliance requirements for OS-level audit, the need for custom InnoDB builds, or performance tuning below the MySQL layer — engineers deploy MySQL on cloud virtual machines. The chapter provides detailed guidance on choosing the right machine type and storage configuration for InnoDB workloads.

The InnoDB buffer pool is the primary sizing input. Your working set — the set of pages accessed regularly — should fit in RAM. A machine that can hold 120% of your working set in RAM will achieve near-zero disk reads in steady state. For write-heavy workloads, the InnoDB redo log flush rate is CPU-bound (AES encryption of log records, crc32 checksums), so CPU speed matters even when queries are simple. General-purpose instances balance vCPU and RAM at roughly 4 GB per vCPU and are appropriate for most OLTP workloads. Memory-optimized instances (e.g., AWS r7g, GCP m3) provide 8–16 GB per vCPU and are appropriate for large in-memory datasets. Compute-optimized instances (e.g., AWS c7g) prioritize raw CPU speed and are appropriate when the bottleneck is query compilation or redo log encryption rather than buffer pool capacity.

Disk Selection in Cloud

Disk selection is arguably more impactful than machine type selection for InnoDB-heavy workloads. The three principal storage options on AWS are representative of cloud storage tiers broadly: gp3 (general-purpose SSD), io1/io2 (provisioned IOPS SSD), and local NVMe (instance store on i3/i4i families).

gp3 volumes decouple IOPS and throughput from volume size — you can provision up to 16,000 IOPS and 1,000 MiB/s independently of the volume size. This makes gp3 cost-effective for most OLTP MySQL workloads. io2 volumes extend to 256,000 IOPS and 4,000 MiB/s but cost significantly more per GB and per IOPS. They are appropriate when the working set exceeds RAM and random read IOPS are the bottleneck — a scenario more common on large reporting or analytics databases. Local NVMe (instance store) provides the lowest latency and highest IOPS of any option, but instance store volumes are ephemeral: data is lost on instance stop or termination. For MySQL, local NVMe is only safe with a synchronous replica for durability — the local disk becomes the performance hot path while the replica provides the durability guarantee.

Cloud Provider Feature Comparison

Aurora, Google Cloud SQL, and Amazon RDS MySQL represent three distinct approaches to managed MySQL. RDS MySQL is the closest to running MySQL yourself — standard MySQL engine, standard InnoDB storage, all the familiar parameters exposed via a parameter group. Cloud SQL is similarly standard-MySQL but adds deep GCP integration: Cloud SQL Proxy, IAM authentication, and Workload Identity for GKE. Aurora is the most divergent: its custom storage engine delivers superior read-replica lag and failover speed, but introduces migration complexity and potential cost surprises at high IOPS.

The chapter recommends evaluating managed MySQL offerings on five axes: storage model (proprietary vs standard), point-in-time recovery granularity, read replica lag and count limits, maximum storage per instance, and the multi-AZ failure model.
