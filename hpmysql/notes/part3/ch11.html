Ch11 · Scaling MySQL

Scaling MySQL is not a single lever but a layered set of architectural decisions — from adding read replicas to sharding to adopting purpose-built middleware — each trading operational complexity for additional capacity headroom.

What Is Scaling

Scaling a database system means increasing its ability to handle more load — more queries per second, more concurrent connections, more data — without degrading latency or availability. The first and most critical decision is whether to scale vertically (making a single node bigger) or horizontally (adding more nodes). These strategies are not mutually exclusive, but the choice of when to stop scaling vertically and begin distributing load is among the most consequential an engineering team will make.

Vertical scaling is attractive because it requires no application changes: upgrade to a 96-vCPU machine with 768 GB of RAM and a PCIe NVMe array, and throughput rises immediately. InnoDB's buffer pool scales with RAM, and more CPU threads reduce contention on the query execution pipeline. However, vertical scaling has a hard ceiling — both physical hardware limits and cost curves that grow super-linearly at the top tier. A single MySQL primary also remains a single point of failure for writes regardless of how large the machine is.

Horizontal scaling distributes load across multiple machines. For MySQL this typically begins with read replicas, progresses to functional decomposition of the schema across multiple clusters, and eventually reaches full horizontal sharding. Each step multiplies operational surface area: more nodes to monitor, more replication lag to reason about, more places for split-brain to occur during a failover.

The decision matrix is roughly: if your working set fits in memory and write throughput is below ~20 k TPS, vertical scaling combined with read replicas is usually sufficient and dramatically simpler. Once your write throughput saturates a single InnoDB instance, or your dataset exceeds the largest available RAM tier by a wide margin, you must distribute writes — either through functional sharding or horizontal sharding.

Read vs Write Workloads

Before choosing a scaling pattern, you must characterize your workload. A read-bound system spends the vast majority of its query budget on SELECT statements — product pages, search results, reporting dashboards. A write-bound system is dominated by INSERT, UPDATE, and DELETE — order ingestion, event pipelines, IoT telemetry. Many systems are mixed but have a clear dominant axis that determines where the bottleneck lives.

Read-bound workloads scale cleanly with additional replicas: the binary log streams writes to each replica, the primary handles all mutations, and a load balancer distributes reads. The replication lag budget becomes the key SLO. Write-bound workloads cannot be relieved by adding replicas — every replica must still apply every write from the primary, so replication lag worsens as write volume climbs. Write-bound systems require either a bigger primary (vertical), sharding (horizontal partition of writes), or a fundamentally different storage model.

A useful heuristic from the book: measure reads-per-second and writes-per-second from Com_select vs Com_insert + Com_update + Com_delete in SHOW GLOBAL STATUS. A read:write ratio above 10:1 typically means read-pool scaling is the right first step. Below 3:1, you are write-bound and replica fanout will not help.

Read Pools with Load Balancing

The simplest horizontal scaling technique for read-heavy MySQL deployments is a read pool: one primary that accepts all writes, and a set of asynchronous replicas that serve all read traffic. The application must be aware of the distinction — or a middleware proxy must enforce it transparently.

ProxySQL is the de-facto standard for MySQL proxy-based load balancing. It operates at the MySQL protocol level, speaking the MySQL wire protocol to both clients and backends. Query routing rules are defined in mysql_query_rules: a rule can match on regex against the query text, the client username, the schema, or the digest hash, and route the query to a named hostgroup. Reads go to the replica hostgroup; writes (or queries touching replication-sensitive tables) go to the primary hostgroup.

ProxySQL also handles multiplexing: a single backend connection can be reused across many client sessions, dramatically reducing the connection overhead on MySQL. It tracks server health via SELECT 1 heartbeats and automatically removes unhealthy nodes from the pool. For replica lag awareness, ProxySQL can query SHOW REPLICA STATUS periodically and demote replicas that exceed a configured lag threshold to a lower-priority hostgroup, ensuring reads do not observe stale data beyond the application's tolerance.

A critical operational detail: mysql_query_rules matching is evaluated in ascending rule_id order and stops at the first match. Rules that explicitly match write patterns (^INSERT|^UPDATE|^DELETE|^REPLACE|^CALL) should have lower rule IDs than the catch-all read rule, to prevent writes from being accidentally routed to replicas. Transactions that mix reads and writes must be pinned to the primary for the entire transaction duration; ProxySQL handles this automatically when it detects a BEGIN or when the client uses an implicit transaction.

Functional Sharding

Functional sharding — also called vertical decomposition or service-per-database — is the technique of breaking a single large MySQL instance into multiple separate clusters, each owning the data for a specific business domain. Instead of one monolithic schema containing users, orders, inventory, payments, and analytics tables, each domain gets its own MySQL cluster with its own primary and replicas.

This pattern scales write throughput because each domain's writes hit a dedicated primary that no longer competes for InnoDB buffer pool space, redo log bandwidth, or lock contention with other domains. It also enables independent tuning: the orders cluster might be configured for durability (innodb_flush_log_at_trx_commit=1, synchronous binlog), while the analytics cluster can trade some durability for throughput (innodb_flush_log_at_trx_commit=2). It simplifies compliance and access control: the payments cluster can have stricter network ACLs and auditing than the catalog cluster.

The primary cost of functional sharding is the elimination of cross-domain JOIN operations. Queries that previously could join users with orders in a single SQL statement now require application-level joins or a separate aggregation layer. This pushes complexity into service code and forces teams to reason explicitly about data consistency across domain boundaries — a problem that was previously invisible inside a monolithic schema.

Horizontal Sharding

When a single domain's data volume or write rate exceeds what one MySQL cluster can handle, horizontal sharding partitions the rows of a table across multiple physically separate MySQL instances called shards. Each shard holds a subset of the data; together, all shards hold the complete dataset. A shard key — typically the primary key or a tenant identifier — determines which shard owns a given row.

Consistent hashing is the most common shard-routing algorithm. The shard key is passed through a deterministic hash function, and the hash space (typically 0–2³² − 1) is divided into virtual nodes (vnodes) assigned to physical shards. When a new shard is added, only the vnodes re-assigned to the new shard need to migrate data — the rest of the ring is undisturbed. This property makes consistent hashing superior to simple modulo hashing for clusters that grow over time.

Cross-shard queries are the central pain point of horizontal sharding. A query like SELECT * FROM orders WHERE status = 'pending' — with no shard-key predicate — must fan out to every shard, gather results, merge and sort them in a scatter-gather coordinator, and return the merged result. Latency is bounded by the slowest shard, not the average. This makes cross-shard analytics extremely expensive and pushes teams toward maintaining a separate denormalized read store (Elasticsearch, BigQuery, ClickHouse) for ad-hoc queries.

Shard rebalancing — moving vnodes from one shard to another — is operationally complex. Data must be migrated while the cluster remains online, queries must be dual-routed during the migration window, and a cutover mechanism must ensure no writes are lost at the moment of transition. Tools like Vitess implement this natively; teams doing bare-metal sharding typically build custom migration scripts using pt-online-schema-change semantics.

Vitess Architecture

Vitess is an open-source sharding middleware originally built at YouTube to scale MySQL horizontally. It wraps MySQL instances with a layer of orchestration that handles shard routing, connection pooling, query rewriting, online schema changes, and resharding — all transparently to the application. Vitess is deployed at Slack, Square, GitHub, HubSpot, and many other high-volume MySQL users.

The key components of Vitess are VTGate, VTTablet, and the topology service. VTGate is a stateless proxy that receives queries from applications, parses and validates them against the VSchema (Vitess's sharding metadata), rewrites scatter queries into per-shard queries, and aggregates results. Because VTGate is stateless, it scales horizontally behind a standard load balancer. VTTablet is a sidecar process that runs alongside each MySQL instance. It handles connection pooling (eliminating the per-connection overhead that crushes MySQL at high concurrency), enforces query timeouts, and mediates with the topology service for leader election. The topology service — typically etcd or ZooKeeper — stores keyspace and shard metadata, current primary information, and shard routing tables.

The VSchema defines keyspaces (logical databases), vindexes (sharding keys and their hash functions), and the mapping of tables to keyspaces. When VTGate receives a query, it resolves the vindex values in the WHERE clause to a set of shard IDs, and routes the query to the corresponding VTTablet instances. Queries with no vindex predicate are scattered to all shards (a full scatter) and merged by VTGate.

Vitess's resharding capability — VReplication — allows an operator to split a shard into two new shards online. VReplication streams row changes from the source shard to the two target shards using a MySQL binlog-like mechanism, backfills historical data, and performs a traffic cutover with sub-second downtime by briefly buffering writes during the switch. This makes Vitess fundamentally different from hand-rolled sharding: the shard topology is mutable without application downtime.

Scaling Pattern Decision Matrix

Choosing a scaling pattern depends on the dominant bottleneck (reads vs writes), the size and complexity of the dataset, team operational maturity, and tolerance for distributed systems complexity. The table below summarizes the four principal options.
