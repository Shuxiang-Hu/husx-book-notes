Ch01 · MySQL Architecture

MySQL's layered architecture separates client connections from query processing and storage, giving operators surgical control over each tier's behavior and tuning.

Logical Architecture

MySQL is organized into three clean tiers. The connection/service layer manages authentication, thread pooling, and presents the client API. Above it sits the query processing layer — the parser, optimizer, and executor. Beneath everything lives a pluggable storage engine layer that handles data layout, caching, and durability. This separation lets MySQL swap storage engines (InnoDB, MyISAM, Memory, NDB) without touching query logic.

Understanding this layering is essential for diagnosis. Slow queries are almost always a problem in the optimizer or the storage engine, not the connection tier. Configuration variables that start with innodb_ reach all the way down to the third tier; variables like max_connections only touch the first.

The parser tokenizes and validates SQL syntax into a parse tree. The optimizer rewrites the tree into an execution plan — choosing join order, index access paths, and whether to use temporary tables. The execution engine then calls the storage engine API in a loop to fetch rows. Knowing that the optimizer is cost-based (not rule-based) explains why identical SQL can behave differently as cardinality estimates drift over time.

InnoDB Storage Engine

InnoDB is MySQL's default and production-grade storage engine. Its architecture centers on three tightly coupled subsystems: the buffer pool (an in-memory page cache), the clustered primary-key index (the actual data layout on disk), and the redo log (write-ahead durability). These three work in concert to deliver ACID transactions at high concurrency.

Clustered Index

Every InnoDB table is physically ordered by its primary key — the B+tree leaf pages contain the full row data, not just key pointers. This is called a clustered index. Accessing a row by primary key is extremely fast because only one B+tree traversal is needed. Secondary indexes, however, store only the primary key value as their "pointer", meaning lookups through a secondary index require a second traversal (the double-dip). Choosing a narrow, monotonic primary key (e.g., BIGINT AUTO_INCREMENT) is therefore one of the highest-leverage schema decisions you can make.

Buffer Pool

The buffer pool is InnoDB's main memory structure — a shared cache of 16 KB data pages. Reads first check the buffer pool; a miss triggers a disk read and the page is warmed into the pool. Dirty pages (modified but not yet flushed to disk) are tracked on a flush list. The buffer pool is subdivided into instances (default: 8) to reduce mutex contention on multi-core hardware. It should typically consume 70–80% of available RAM on a dedicated MySQL host.

Redo Log

Before modifying a buffer pool page, InnoDB first writes a compact record of the change to the redo log — a fixed-size circular file on disk. This is the write-ahead log (WAL) pattern. On crash recovery, InnoDB replays redo log entries to bring data files to a consistent state, then uses the undo log to roll back any transactions that were in progress at the time of the crash. The redo log size determines how long a crash recovery takes and how frequently dirty pages must be flushed.

Concurrency Control

MySQL implements concurrency control through a hierarchy of locks. At the coarsest level, a table lock blocks all readers and writers; at the finest level, InnoDB's row locks allow many concurrent readers on the same table. The tradeoff is overhead: row locks require more memory and CPU to acquire and release, but they dramatically reduce contention under mixed OLTP workloads.

Read/Write Locks

A shared (read) lock can be held by multiple threads simultaneously — many readers can proceed in parallel. An exclusive (write) lock is held by only one thread and blocks all other readers and writers. InnoDB acquires row-level exclusive locks implicitly on UPDATE, DELETE, and INSERT … ON DUPLICATE KEY UPDATE. Explicit shared locks are requested with SELECT … LOCK IN SHARE MODE; explicit exclusive locks with SELECT … FOR UPDATE.

Lock Granularity

InnoDB supports three lock granularities: row locks on individual index records, gap locks on the gap between index records (important for preventing phantom reads in REPEATABLE READ), and next-key locks (row lock + gap lock on the preceding gap). Gap locks exist only in REPEATABLE READ and are released when the isolation level is set to READ COMMITTED.

Transactions

Transactions package multiple SQL statements into a single atomic unit. InnoDB is fully ACID compliant: Atomicity (all-or-nothing), Consistency (schema constraints are enforced), Isolation (concurrent transactions behave as if serialized), and Durability (committed data survives crashes). The redo log and undo log together implement atomicity and durability; locking and MVCC implement isolation.

Isolation Levels

SQL-92 defines four isolation levels, each relaxing isolation constraints for better concurrency. MySQL defaults to REPEATABLE READ — a pragmatic balance that prevents dirty and non-repeatable reads while allowing phantom reads in theory (though InnoDB's next-key locks largely prevent them even at this level).

Deadlock Cycle

A deadlock occurs when two (or more) transactions each hold a lock the other needs. InnoDB detects cycles in the wait-for graph and automatically kills the transaction with the least amount of undo work, rolling it back. The victim receives error 1213. Well-designed applications always retry on deadlock. You can monitor deadlocks via SHOW ENGINE INNODB STATUS and the innodb_deadlock_detect variable.

MVCC

Multi-Version Concurrency Control (MVCC) is InnoDB's answer to the classic readers-block-writers problem. Instead of taking shared locks, readers access a consistent snapshot of the data as it existed at the start of their transaction. Writers proceed concurrently by creating new versions of modified rows in the undo log. Readers compare version timestamps against their own read view to determine which row version is visible.

Every InnoDB row has two hidden system columns: DB_TRX_ID (the transaction ID of the last writer) and DB_ROLL_PTR (a pointer into the undo log chain for that row). A read view records the lowest and highest active transaction IDs at snapshot creation time. If a row's DB_TRX_ID is newer than the snapshot, InnoDB follows the undo log chain backwards until it finds a version the transaction can see.

MVCC has a crucial operational implication: long-running transactions accumulate undo log. The purge thread cannot remove old undo records as long as any open read view might still need them. A transaction open for hours can cause the undo tablespace to grow dramatically and degrade performance of all subsequent queries that must traverse the extended undo chain. This is why monitoring INFORMATION_SCHEMA.INNODB_TRX for long-running transactions is a production necessity.

Replication Overview

MySQL replication propagates changes from a source (primary) to one or more replicas using the binary log (binlog). The binlog records all committed data-changing events in either statement, row, or mixed format. Replicas maintain a relay log — a local copy of the binlog — and apply events using one or more parallel SQL threads. This asynchronous pipeline is the backbone of MySQL high availability and read scaling.

Chapter 9 covers replication in depth. For now, the key architectural points are: (1) replication is asynchronous by default — the source does not wait for the replica to acknowledge a transaction before committing; (2) semi-synchronous replication adds a one-ack guarantee from at least one replica before returning to the client; (3) Group Replication / InnoDB Cluster provides synchronous majority-quorum writes for true fault tolerance.
