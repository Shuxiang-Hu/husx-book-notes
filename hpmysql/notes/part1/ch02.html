Ch02 · Monitoring in a Reliability Engineering World

Effective MySQL observability begins by framing the database as a service with formal reliability targets — SLIs, SLOs, and SLAs — then instrumenting the four golden signals to detect degradation before users do.

SLI / SLO / SLA Hierarchy

The reliability engineering vocabulary borrowed from Google SRE gives teams a precise shared language for discussing database health. A Service Level Indicator (SLI) is a specific, quantifiable measurement — for example, the 99th-percentile query latency measured over a rolling 5-minute window. A Service Level Objective (SLO) is the internal target your team commits to: "p99 query latency < 50 ms, 99.9% of the time over a 30-day window." A Service Level Agreement (SLA) is the external, contractual promise to customers — often slightly looser than your SLO, to give the team headroom.

The hierarchy flows outward: concrete SLI measurements roll up into SLO burn-rate alerts, which inform the SLA you can honestly guarantee to customers. Breaking this chain — agreeing to an SLA without first defining measurable SLIs and achievable SLOs — is the original sin of reliability engineering.

For MySQL specifically, the most common SLIs are: query latency percentiles (p50, p95, p99), error rate (connection refused + query errors / total queries), throughput (queries per second), and availability (fraction of 1-second windows where the server accepted connections).

Four Golden Signals

Google's SRE book identifies four universal signals applicable to any serving system. For MySQL, each maps directly to specific metrics:

  • Latency — How long individual queries take. Track p50, p95, p99, and max. Distinguish successful query latency from error latency (errors can be fast but masked failures).
  • Traffic — Volume of demand. For MySQL: QPS broken down by statement type (Com_select, Com_insert, Com_update, Com_delete), connections per second, active threads.
  • Errors — Rate of failed requests. Connection errors (Connection_errors_max_connections), aborted clients, query errors from the error log.
  • Saturation — How "full" the service is. CPU utilization, InnoDB buffer pool hit rate (a falling hit rate signals memory saturation), disk I/O utilization, replication lag.

These four signals form a minimal complete monitoring dashboard. If all four are green, almost all user-visible problems are covered. Teams that instrument only throughput and uptime miss the most common class of MySQL incident: the latency spike that leaves the database technically "up" but user-facing timeouts exploding.

Defining What to Measure

Averages lie. A workload with 99% of queries completing in 1 ms and 1% timing out at 30 seconds shows an "average latency" of about 300 ms — technically true but operationally misleading. Percentile-based histograms reveal the true latency distribution and are the correct tool for measuring MySQL query performance.

The authors recommend instrumenting three percentile thresholds: p50 (median — typical user experience), p95 (near-worst-case most users see), and p99 (SLO-relevant threshold — the worst 1 in 100 queries). Some teams also track p999 for especially latency-sensitive services. MySQL 8.0's Performance Schema exposes per-digest histogram data via events_statements_histogram_by_digest, removing the need for application-side instrumentation.

When choosing SLI thresholds, start from the user's tolerance, not from what the system currently achieves. If a human notices latency above 100 ms, your p99 SLO should be 50 ms with a 50% headroom buffer, not 95 ms because "that's where the data clusters."

Proactive Monitoring

Reactive monitoring — paging when users complain — is a sign of an immature operations practice. Proactive monitoring fires alerts based on burn rate: how fast you are consuming your error budget relative to the SLO window. A 14× burn rate alert fires when the system is consuming error budget fourteen times faster than the 30-day budget allows — which corresponds to exhausting a month's budget in about 51 hours if left unchecked.

Google's multiwindow, multi-burn-rate alerting strategy pairs a long window (1 hour) with a short window (5 minutes) at each severity level. The long window prevents spurious pages from brief spikes; the short window ensures rapid detection of sustained degradation. This dual-window approach is directly applicable to MySQL SLO alerting on query latency, error rate, and availability.

For MySQL specifically, proactive signals include: rising Threads_running (approaching max_connections), increasing innodb_row_lock_waits, the undo log tablespace growing (long-running transactions), and replication lag trending upward before it becomes a crisis.

Long-Term Performance Measurement

Short-window alerting catches incidents; long-window trend analysis prevents them. By graphing capacity metrics over weeks and months — buffer pool hit rate, QPS growth, slave lag trend, disk utilization growth rate — teams can project when the next capacity cliff will occur and provision before it hits.

Common long-term metrics to track in MySQL: (1) QPS growth rate — project when you will need the next read replica; (2) Data file growth — project when you need to expand disk; (3) Replication lag baseline — rising baselines indicate that the replica apply thread is falling behind write throughput; (4) Buffer pool eviction rate — a rising eviction rate means the working set is outgrowing memory.

Monitoring Tools

The MySQL monitoring ecosystem has matured considerably. The authors recommend choosing a tool that can collect per-digest query latency histograms (not just server-level averages), persist raw data for trend analysis, and integrate with your existing alerting pipeline. No single tool excels at everything — most production environments combine two or three.

Prometheus + mysqld_exporter

The open-source standard. The mysqld_exporter scrapes MySQL's SHOW GLOBAL STATUS, SHOW SLAVE STATUS, and Performance Schema tables, exposing them as Prometheus metrics. Query-level granularity requires pairing with a digest table scraper or the PMM Query Analytics component. Grafana dashboards provide visualization. Total cost: infrastructure only. Scales to any number of MySQL instances with a single Prometheus cluster.

Percona Monitoring and Management (PMM)

PMM is Percona's batteries-included MySQL observability platform. It ships pre-built Grafana dashboards, a Query Analytics UI for per-digest latency analysis, and integrates with both MySQL and MongoDB. PMM uses the slow query log or Performance Schema as its query data source. It is the most MySQL-specific option in the ecosystem and the best default choice for teams without dedicated monitoring engineers.

Datadog

Datadog's MySQL integration combines infrastructure-level metrics (server status variables, replication lag) with the Database Monitoring (DBM) add-on, which collects per-query execution plans and wait event data from Performance Schema. DBM costs extra but eliminates the need to maintain self-hosted monitoring infrastructure. Best for teams already standardized on Datadog for their broader observability stack.
