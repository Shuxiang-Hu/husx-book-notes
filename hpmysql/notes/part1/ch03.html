Ch03 · Performance Schema

Performance Schema is MySQL's built-in low-overhead instrumentation engine — a system database of in-memory tables that expose exactly what the server is doing at any given moment, from individual statement execution stages to memory allocations and mutex waits.

Architecture Overview

Performance Schema (P_S) follows a classic producer-consumer architecture. Instruments are points in the MySQL source code that collect measurement data — a function call, a lock acquisition, a file read. Consumers are the in-memory tables that receive and aggregate that data. When an instrument fires, it only delivers data to consumers that are currently enabled, keeping overhead proportional to what you actually need to measure.

This design has two key implications. First, you pay only for what you enable — a server with all instruments and consumers disabled has near-zero overhead from P_S. Second, data collection is entirely in-memory with ring-buffer semantics; there is no persistence across restarts. Schema-level configuration (which instruments and consumers are enabled) can be persisted to a configuration file, but the collected data itself is ephemeral.

MySQL 8.0 enables Performance Schema by default with a balanced set of instruments and consumers active. The performance_schema system variable must be set at startup to enable or disable it entirely; you cannot change this at runtime.

Instrument Elements

Instrument names follow a hierarchical naming convention: category/subcategory/.../leaf_name. For example, statement/sql/select instruments SELECT statements; wait/io/file/innodb/innodb_data_file instruments InnoDB data file reads and writes. This hierarchy enables selective enabling — you can turn on all statement instruments with a single wildcard pattern while leaving I/O instruments disabled.

Each instrument has two configuration flags: ENABLED (whether it fires at all) and TIMED (whether it records timing information). Timing adds overhead; if you only need counts (not latencies), you can set TIMED=NO for a given instrument to reduce impact.

The instrument hierarchy also reflects the execution model. Global instruments aggregate across the entire server instance. Thread instruments track per-connection state. Statement instruments capture each SQL statement. Stage instruments track sub-steps within a statement (e.g., "Sending data", "Creating sort index"). This four-level hierarchy — global → thread → statement → stage — maps precisely to the granularity at which you would diagnose performance problems.

Consumer Organization

Consumers form a dependency tree — a child consumer only receives data if its parent is also enabled. The root is global_instrumentation: if this is disabled, nothing works. Beneath it are thread_instrumentation (per-connection data) and the statements_digest consumer (the global digest table, which does not require thread_instrumentation). This design means you can enable digest-level aggregation (the most useful for identifying slow query patterns) at minimal overhead, without enabling per-thread history tables (which are more expensive).

The history consumers (events_statements_history, events_statements_history_long) maintain ring buffers of recent events per thread or globally. History tables are expensive because they retain per-event rows; in production you typically enable them for diagnosis periods rather than permanently. The summary consumers aggregate by digest, user, host, or account — these are low overhead and permanently useful.

Configuration

Performance Schema configuration is done via two control tables: setup_instruments and setup_consumers. Both are live — changes take effect immediately without a server restart. This makes it safe to enable additional instruments for a diagnostic session and then disable them once the investigation is complete.

The canonical pattern for enabling statement instrumentation is:

UPDATE performance_schema.setup_instruments
SET ENABLED='YES', TIMED='YES'
WHERE NAME LIKE 'statement/%';

UPDATE performance_schema.setup_consumers
SET ENABLED='YES'
WHERE NAME IN (
  'events_statements_history',
  'events_statements_history_long'
);

To minimize overhead in production: enable only statements_digest and the global summary tables permanently; enable per-thread history consumers only during active diagnosis; keep I/O and memory instruments disabled unless specifically investigating those subsystems.

MySQL 8.0 also introduces setup_threads to control instrumentation per background thread and setup_objects to filter instrumentation by schema/table, allowing you to, for example, exclude performance_schema and information_schema tables from table I/O tracking to reduce noise.

Using Performance Schema

The Performance Schema becomes useful the moment you start querying it. The three most important use cases are: identifying slow query patterns via the digest table, understanding lock contention, and tracking memory usage.

Statement Analysis via Digest Table

The events_statements_summary_by_digest table aggregates all statements into canonical "digests" — normalized forms where literals are replaced with ? placeholders. This lets you identify the query pattern consuming the most total server time, even if no individual execution is slow:

SELECT DIGEST_TEXT, COUNT_STAR, AVG_TIMER_WAIT/1e9 AS avg_ms,
       SUM_TIMER_WAIT/1e9 AS total_ms,
       SUM_ROWS_EXAMINED, SUM_ROWS_SENT
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;

Lock Analysis

The data_locks and data_lock_waits tables (in performance_schema since MySQL 8.0, previously in information_schema) show current lock state. Joining these tables exposes the full blocker-victim chain, which is essential for diagnosing lock contention incidents that don't manifest as deadlocks.

Memory Tracking

Memory instruments (memory/*) track allocations and deallocations per code component. The memory_summary_global_by_event_name table shows current usage and high-water marks. This is the correct tool for diagnosing unexpected memory growth that innodb_buffer_pool_size alone cannot explain — for example, large sort buffers, prepared statement caches, or the table open cache.

sys Schema

The sys schema (bundled with MySQL 5.7.7+ and enabled by default in 8.0) is a collection of views and stored procedures layered on top of Performance Schema. It translates raw P_S data into human-readable formats — converting picosecond timer values to "10.23 ms", bytes to "2.40 GiB", and normalizing digest text. The sys schema does not collect any additional data; it is purely a presentation layer.

The most commonly used sys views are: sys.statements_with_runtimes_in_95th_percentile, sys.schema_tables_with_full_table_scans, sys.innodb_buffer_stats_by_schema, and sys.host_summary. The stored procedure sys.ps_trace_statement_digest() performs a real-time profiling session for a specific query digest.
