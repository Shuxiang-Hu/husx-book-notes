Chapter 5: Replication

Keeping copies of data on multiple nodes for latency, availability, and read throughput — and the hard problems that arise.

Three replication architectures, each with different consistency and availability trade-offs.

§5.1

Single-Leader Replication

Leader accepts all writes. Sync follower ACKs before leader confirms to client (guaranteed up-to-date). Async follower may lag (fast but can lose data on failover).

Replication Lag Problems

Three replication lag anomalies and their solutions. Each requires different guarantees beyond eventual consistency.

§5.2

Multi-Leader Replication

Use cases: (1) Multi-datacenter: one leader per DC, DCs replicate asynchronously — lower write latency, DC failure tolerance. (2) Clients with offline operation (CouchDB). (3) Collaborative editing (Google Docs).

The fundamental problem: the same data may be modified concurrently in two DCs. Write conflicts are inevitable and must be resolved.

Conflict Resolution

  • Conflict avoidance: route all writes for a given record through one DC-leader (fails if that DC fails).
  • Last Write Wins (LWW): each write gets a timestamp; highest timestamp wins. Loses data. Cassandra default. Clock skew makes it unreliable.
  • Merge values: concatenate (e.g., union of shopping carts). Works for some types.
  • Custom conflict resolution: on write (Riak) or on read (CouchDB exposes conflicting "siblings" to application).
  • CRDTs: data structures that automatically merge without conflicts (counters, sets, maps).

Multi-leader replication topologies. All-to-all most resilient but has message ordering issues. Star and circular have single points of failure.

§5.3

Leaderless Replication (Dynamo-style)

Amazon Dynamo (2007), Cassandra, Riak, Voldemort. Client (or a coordinator node) sends writes to multiple replicas simultaneously. On read, client contacts multiple replicas and resolves conflicts using version numbers.

Quorums

Quorum: with n=5, w=3, r=3 — any read set must overlap with the write set by at least 1 node, guaranteeing the latest value is visible.

Read repair: client reads from multiple replicas; detects stale value; writes fresh value back to stale replica. Anti-entropy: background process that reconciles differences. Sloppy quorums: during partition, accept writes to any available nodes (hinted handoff) — more availability, weaker consistency.
