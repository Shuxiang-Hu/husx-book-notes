Part II — Distributed Data

Chapter 6 · Partitioning

Partitioning (sharding) breaks a large dataset across multiple nodes so that each node holds only a subset of the data. Combined with replication it enables horizontal scalability — but choosing how to partition and how to route requests requires careful thought.

Why Partition?

A single machine has finite disk, RAM, and CPU. Replication copies the same data to more machines; partitioning splits different data across machines. Together they let a cluster scale to petabytes while each node handles only a fraction of the total load.

The goal is fair load distribution. An uneven split — where one partition receives far more reads/writes than others — is called a hot spot.

Partitioning Strategies

Consistent Hashing — Originally proposed for CDNs. Each node is assigned multiple points on a hash ring; a key is stored on the first node clockwise from its hash. Adding/removing a node only moves a fraction of keys. Modern databases like Cassandra and DynamoDB use variants of this idea.

Secondary Indexes & Partitioning

Primary key partitioning is straightforward, but secondary indexes don't map cleanly onto partitions. Two approaches exist:

ApproachRead costWrite costExample systems
Document-partitioned (local)Scatter-gather all N partitionsWrite one partitionMongoDB, Elasticsearch, Riak
Term-partitioned (global)Query one index partitionUpdate K index partitions (often async)DynamoDB GSI, BigTable

Rebalancing Partitions

Nodes are added/removed over time. Rebalancing must move data to restore balance while keeping the database available.

Auto vs. Manual Rebalancing — Fully automatic rebalancing is convenient but dangerous: a node appears slow (e.g. GC pause), cluster decides to move its partitions, network gets saturated, other nodes become slow, triggering a cascade. Couchbase, Riak, and Voldemort generate a suggested rebalancing plan automatically but require operator approval to execute.

Partitioning + Replication Together

In practice, partitioning is almost always combined with replication. Each partition has a leader and followers across different nodes. A single node will typically be the leader for some partitions and a follower for others.

The choice of partitioning scheme is largely independent of replication scheme — they compose orthogonally.

Key Takeaways

Goal
Spread data and query load evenly; avoid hot spots.
Range partitioning
Keys in sorted order — efficient range scans, but can create hot spots on sequential writes (e.g., timestamps).
Hash partitioning
Uniform distribution, but loses sort order. Consistent hashing minimises data movement on cluster resize.
Secondary index — document
Each partition indexes only its own documents. Reads scatter-gather across all partitions.
Secondary index — term
Global index, itself partitioned by term. Reads hit one partition; writes update multiple index partitions (often async).
Rebalancing
Fixed number of logical partitions (Riak/Elasticsearch) or dynamic splitting (HBase). Avoid hash-mod-N.
Request routing
Any node + forwarding; dedicated routing tier; or client-side routing. ZooKeeper often used for coordination.
