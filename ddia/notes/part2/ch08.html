Chapter 8 · The Trouble with Distributed Systems

Distributed systems face a unique class of problems: partial failures are the norm, not the exception. Networks drop packets, clocks drift, garbage collectors pause the world, and nodes may be slow without knowing it. This chapter catalogs these failure modes so we can reason about them precisely.

Network Unreliability

Unlike a single computer where operations either succeed or fail atomically, distributed systems face partial failures. When a message is sent and no reply arrives, there are at least three equally plausible explanations:

Timeouts are the only reliable detection mechanism — but they don't tell you what happened. A long timeout avoids false positives; a short timeout detects failures faster but may declare a slow node dead. Choose based on application latency requirements and expected network variance.

Synchronous vs. Asynchronous Networks

The telephone network (circuit-switched) allocates a fixed bandwidth slice per call — latency is bounded. The internet (packet-switched) is designed for bursty traffic with no bandwidth reservation — latency is unbounded.

TCP queues packets in buffers; a full buffer causes queuing delay. This is why tail latency (p99, p999) matters more than mean latency for distributed systems.

Unreliable Clocks

Every machine has its own clock, drifting slightly from real time. NTP can synchronize to within a few milliseconds on a LAN — worse over the internet. Clock problems cause subtle, hard-to-reproduce bugs.

TrueTime (Google Spanner) — GPS receivers and atomic clocks in each datacenter. TrueTime exposes an interval [earliest, latest] within which the true time lies. Spanner waits for the uncertainty window to pass before committing a read-write transaction, ensuring globally consistent snapshots. The interval is typically <7 ms.

Fencing Tokens — A monotonically increasing number issued every time a lock or lease is granted. Every write to the storage service must include the fencing token; the service rejects writes with a token older than the one it last saw. Even a zombie leader (woken from GC pause with an expired lease) cannot corrupt data.

Byzantine Faults

So far we assumed nodes may crash or be slow, but always follow the protocol honestly. Byzantine faults are worse: a node may send deliberately incorrect data — corrupted, malicious, or buggy.

Most databases and distributed systems do not defend against Byzantine faults — they assume nodes in a trusted datacenter behave honestly. Byzantine fault tolerance is primarily needed for:

  • Blockchain / cryptocurrency (untrusted participants)
  • Aerospace systems (cosmic ray bit flips)
  • Multi-organization coordination

System Models

To reason rigorously about distributed algorithms, we pick a system model — a set of assumptions about what can fail:

System ModelNetworkClocksProcess FaultsUsed for
Synchronous Bounded delay Bounded drift Crash-fail Theoretically clean; unrealistic for internet
Partially synchronous Usually bounded; rarely unbounded Usually bounded Crash-recovery Most real-world algorithms (Raft, Paxos)
Asynchronous No bounds at all No clocks Crash-fail Very conservative; FLP impossibility applies
FLP Impossibility — In a purely asynchronous system with even one possible crash, no algorithm can guarantee that consensus is reached in finite time (Fischer, Lynch, Paterson 1985). This doesn't mean consensus is impossible in practice — it means you must either use timeouts (partial synchrony) or accept that the algorithm may sometimes block. Raft and Paxos make progress under partial synchrony.
The Core Thesis of Chapter 8 — In a distributed system, there is no global shared memory, no accurate global clock, and no way to tell if a remote node is dead or just slow. All knowledge is local and based on messages that may be delayed. Algorithms must be designed to tolerate these realities rather than assuming them away.

Key Takeaways

Network
Asynchronous, unreliable. Timeouts are the only detection mechanism. Cannot distinguish "lost request" from "slow response" from "lost reply".
Clocks
Each node has a local clock that drifts. NTP gives millisecond accuracy at best. Never use timestamps to order distributed events — use logical clocks.
Process pauses
GC, swapping, hypervisor migration can pause a process for seconds. The process wakes up with no idea time has passed. Expired leases become dangerous.
Fencing tokens
Monotonically increasing token per lock grant. Storage rejects writes with old tokens. Protects against zombie leaders acting on expired leases.
Byzantine faults
Nodes may send arbitrary incorrect data. Most distributed databases don't defend against this — only relevant in adversarial or multi-org environments.
System model
Most real algorithms assume partially synchronous network and crash-recovery faults. FLP impossibility applies to fully asynchronous systems.
