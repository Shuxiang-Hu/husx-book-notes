Part II — Distributed Data

Chapter 7 · Transactions

A transaction groups multiple reads and writes into a single logical unit: either the whole thing succeeds (commit) or the whole thing fails (abort/rollback). Transactions are the primary tool databases provide for tolerating faults — but they come with real costs and many systems now offer weaker guarantees.

ACID — The Classic Safety Properties

BASE ≠ ACID — NoSQL vendors coined "BASE" (Basically Available, Soft state, Eventually consistent) partly as a marketing counter to ACID. The comparison is misleading: the two terms don't sit on a spectrum; they describe different design priorities. ACID's weakest link is Isolation — most systems default to weaker isolation than full serializability.

Isolation Levels & Race Conditions

Full isolation (serializability) is expensive. In practice, databases offer a spectrum of isolation levels, each tolerating different concurrency bugs:

Write Skew Pattern — Two doctors each check if at least one other is on call, find yes, and both go off-call. Neither update conflicts at the row level, yet the invariant (≥1 doctor on call) is violated. This pattern — read a set, make a decision, write based on that decision — is not prevented by snapshot isolation. It requires materialising conflicts or serializable isolation.

Multi-Version Concurrency Control (MVCC)

MVCC is the standard implementation of snapshot isolation. Instead of locking, the database keeps multiple versions of each row — each transaction sees the version that existed at its start time.

Implementing Serializability

Preventing Lost Updates

The lost-update problem arises from read-modify-write cycles. Several solutions exist, depending on the level of the stack:

Atomic operations
UPDATE counters SET value = value + 1 WHERE key = 'x' — the DB handles the RMW atomically. No application-level read needed. Best solution when sufficient.
Explicit locking
SELECT ... FOR UPDATE — locks the rows for the duration of the transaction. Other txs block. Application controls the logic.
Automatic detection
DB detects lost updates and aborts the offending transaction. Requires snapshot isolation (MVCC). PostgreSQL does this automatically.
Compare-and-set (CAS)
UPDATE t SET value = new WHERE value = old — only update if value hasn't changed. Fails safely if it has; application must retry. Check the DB doesn't apply CAS from an old snapshot.

Key Takeaways

ACID
Atomicity (abortability) and Durability are DB guarantees. Isolation is expensive and often weakened. Consistency is an application concern.
Isolation levels
Read Committed → Snapshot Isolation → Serializable. Most defaults are Read Committed or Snapshot; full serializability is rare due to performance cost.
MVCC
Standard implementation of snapshot isolation. Multiple row versions; readers never block writers; GC removes old versions when no longer needed.
Write skew
The hardest anomaly: two concurrent txs each read a shared condition, make a decision, and write — each correct in isolation but together violate the invariant. Only serializability prevents it.
Serializability options
Actual serial (single-threaded, RAM datasets), 2PL (locks, deadlocks), SSI (optimistic, MVCC-based, high throughput). 2PL is the historical default; SSI is the modern preferred approach.
