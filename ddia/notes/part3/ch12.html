Chapter 12 · The Future of Data Systems

The final chapter synthesizes the book's themes: how should we compose the tools we've learned about into a coherent data architecture? What are the limits of current approaches? Kleppmann proposes the dataflow paradigm — unbundling the database, using the event log as the integration backbone, and putting correctness and ethics at the center.

Lambda Architecture vs Kappa Architecture

When batch processing produces correct but late results and stream processing produces fast but approximate results, a common pattern combines them:

ArchitectureBatch LayerStream LayerComplexity
LambdaSeparate (Spark/MR)Separate (Storm)High — duplicate logic, two systems
KappaSingle stream processor with replayable log (Flink + Kafka)Lower — one codebase, one runtime

Unbundling the Database

A traditional relational database bundles together: storage engine, query planner, transaction manager, replication, index maintenance, caching. Modern data systems unbundle these concerns across specialized tools:

The Log as Integration Backbone — The event log (e.g., Kafka) plays the role that Enterprise Service Buses tried to play, but better: it's durable, replayable, and decoupled. Producers write events; any number of consumers build their own views. This is the "write once, read many" principle applied to data integration.

End-to-End Correctness

A stream processor may guarantee exactly-once delivery — but that doesn't mean the end-to-end application is correct. Consider the user clicking "pay" twice:

Exactly-once in the processor ≠ exactly-once end-to-end — The storage layer, the client, the network, and side effects (emails, payment charges) all need their own idempotency guarantees. There is no magic database feature that buys you end-to-end correctness — it must be engineered at every boundary.

Dataflow vs. Request/Response

Request/Response (Synchronous)

Client sends request → waits → server responds. Simple mental model but:

  • Tight coupling — client must know server address
  • Client blocks waiting for response
  • Hard to fan-out to many systems atomically
  • Difficult to maintain consistency across services

Dataflow (Asynchronous / Event-Driven)

Producer writes event to log → consumers react independently. Looser coupling:

  • Producer doesn't know who consumes
  • Consumer decides when to process
  • Easy to add new consumers (no producer change)
  • Replay enables rebuilding derived state

Ethics of Data Systems

Kleppmann closes with a rare ethical discussion for a technical book. The same data systems that enable personalisation and fraud detection also enable surveillance, discrimination, and manipulation. Technical choices are moral choices.

Book-Wide Synthesis

Key Takeaways

Lambda vs Kappa
Lambda duplicates logic across batch and stream layers. Kappa simplifies by using a single stream processor with a replayable log for both real-time and historical reprocessing.
Unbundling the database
Modern data architectures separate concerns: a durable event log (Kafka) acts as the source of truth; specialized stores (OLTP, search, cache, warehouse) are derived and kept in sync by consuming the log.
End-to-end correctness
Exactly-once in the stream processor is necessary but not sufficient. Every system boundary — client retries, sinks, third-party APIs — needs its own idempotency guarantees.
Dataflow over request/response
Event-driven architectures decouple producers from consumers, enable fan-out, and allow replay for rebuilding derived state. The log is the integration backbone.
Ethics
Data systems have real-world consequences — surveillance, discrimination, manipulation. Engineers are responsible for the systems they build. "Can we build it?" and "Should we?" are separate questions.
