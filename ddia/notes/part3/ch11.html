Chapter 11 · Stream Processing

Batch processing runs periodically on bounded datasets. Stream processing runs continuously on unbounded event streams — enabling real-time derived data with seconds of latency instead of hours. This chapter covers messaging systems, event sourcing, stream processing operators, and the critical problem of time.

Event Sourcing & Change Data Capture

CQRS — Command Query Responsibility Segregation — Separates writes (commands → append events to log) from reads (queries → read a pre-computed projection). Derived read models are built by consuming the event log. Enables highly optimised read paths (e.g., denormalised tables, full-text indexes) without compromising write simplicity.

Fault Tolerance & Exactly-Once

GuaranteeWhat It MeansHow Achieved
At-most-once Some events may be lost; never duplicated Fire-and-forget. Simple but lossy.
At-least-once No events lost; may be duplicated Retry on failure. Idempotent consumers can tolerate duplicates.
Exactly-once No loss, no duplicates Idempotent writes + transactional offsets (Kafka), or distributed snapshots (Flink Chandy-Lamport)

Key Takeaways

Log-based brokers
Kafka and Kinesis: durable append-only log, multiple consumer groups, replay at any offset. Preferred over queue-based brokers for stream processing and CDC.
Event sourcing
Store all changes as an immutable event log; derive current state by replaying. Full audit trail; flexible derived views; pairs naturally with CQRS.
Event time vs processing time
Events may arrive late or out of order. Use event time with watermarks (estimate of completeness) to produce correct windowed aggregations. Handle late events explicitly.
Windows
Tumbling (fixed non-overlapping), sliding (overlapping), session (activity-based). Flink and Kafka Streams provide all three with configurable watermark strategies.
Exactly-once
Achieved via idempotent writes + transactional offsets (Kafka), or distributed snapshots (Flink). At-least-once with idempotent consumers is simpler and often sufficient.
