Part III — Derived Data

Chapter 10 · Batch Processing

Part III shifts from storing and retrieving data to deriving new data from existing data. Batch processing reads a large input dataset, runs a computation, and writes an output — without user interaction. MapReduce popularised this at web scale; modern engines like Spark improve upon it dramatically.

Three Kinds of Systems

The Unix Pipeline — Batch Processing's Ancestor

Before MapReduce, the Unix pipeline achieved the same shape: each tool does one thing well, tools communicate via stdin/stdout (the "uniform interface"), and pipelines compose them without modification.

Limitations: runs on one machine, no fault tolerance, sort requires data to fit on disk. MapReduce distributes this pattern across thousands of nodes.

Joins in Batch Processing

Handling Hot Keys — If a small number of keys (e.g., a celebrity userId) appear millions of times, a single reducer gets all of them. Solution: salting — randomly append a suffix (0–9) to hot keys when writing, then query with all suffixes and union the results. Or replicate the small-side table many times and use a broadcast join.

Output of Batch Jobs

Batch jobs produce derived data — datasets derived from raw inputs. Common uses:

Search indexes
Full-text search index files built over a corpus. Lucene segment files written by reducers, then loaded into search servers. Incremental updates are new batch runs.
Key-value store snapshots
Produce a static key-value store (e.g., HBase bulk-load, LevelDB SST files) from a batch job. Servers swap to the new version atomically.
Recommendation models
Train a collaborative-filtering or ML model. Write model parameters to distributed store. Serving layer reads parameters for real-time inference.
Aggregated metrics
Daily/hourly counts written to a time-series database or data warehouse for dashboards.
Outputs as Immutable Files — Batch job outputs are usually written to new files/directories, never modifying input data. This makes jobs easy to re-run (idempotent), rollback, A/B test, and audit.

Key Takeaways

Batch vs. OLTP
Batch reads immutable inputs, writes new outputs. No user-facing latency. Key metric is throughput, not response time.
MapReduce
Two-stage (map + shuffle/sort + reduce) over HDFS. Fault-tolerant by re-running tasks. Intermediate results materialised to HDFS — flexible but slow.
Joins
Sort-merge join for large inputs (shuffle by key); broadcast hash join when one side fits in RAM (no shuffle). Hot keys need salting or replication.
Dataflow engines
Spark/Flink/Tez eliminate unnecessary materialisation by pipelining stages in memory. Dramatic speedups for iterative ML/graph algorithms.
Derived data philosophy
Separating storage (immutable raw data) from computation (batch transforms) enables reprocessing the entire history when business logic changes — a powerful audit and evolution capability.
