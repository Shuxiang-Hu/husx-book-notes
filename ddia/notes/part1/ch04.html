Chapter 4: Encoding and Evolution

Programs change; data must remain readable by old and new code. Serialization formats, schema evolution, and the three modes of dataflow.

§4.1

Backward & Forward Compatibility

Rolling upgrades mean old and new versions of code run simultaneously. Data written by the new schema must be readable by old code (forward compatibility), and data written by old code must be readable by new code (backward compatibility).

Both directions of compatibility are required during rolling upgrades and for data that outlives code.

§4.2

Encoding Formats

Relative encoded sizes for the same simple record. Binary formats eliminate field names from the wire; schema-based formats are most compact.

Language-Specific Formats

Java Serializable, Python pickle, Ruby Marshal. Avoid: language-specific (can't share data cross-language), security issues (arbitrary class deserialization), versioning afterthought, bad performance.

JSON / XML / CSV

  • JSON: no integer/float distinction; no binary (base64 workaround); optional schema (JSON Schema).
  • XML: verbose; no numeric types; namespace confusion.
  • CSV: no schema; comma/newline ambiguity.
  • All: human-readable; fine for interchange; slow for bulk; schema optional.

Thrift and Protocol Buffers

Require a schema (IDL). Encode field tag numbers (integers) instead of field names → compact. Adding a new optional field with a new tag is forward+backward compatible. Changing a tag number breaks everything. Cannot safely add required fields after initial deploy. required/optional/repeated modifiers. Protobuf is nearly identical to Thrift CompactProtocol.

Avro

No field tags. No type annotations in binary. Values concatenated in schema field order. Requires both writer's schema and reader's schema. Schema resolution matches fields by name. Missing field in writer → use reader's default. Extra field in writer → ignore. Very compact. Schema stored once per file or in a registry (schema version ID per row). Excellent for Hadoop/Kafka pipelines.

Avro schema resolution: fields matched by name. Extra writer fields ignored; missing reader fields filled with defaults.

§4.3

Modes of Dataflow

The three ways data flows between processes. Each has different encoding requirements and compatibility guarantees.

REST vs RPC

RPC tries to make a network call look like a local function call — a leaky abstraction. Network calls can fail in ways local calls can't: packet loss, variable latency, timeouts, retries causing duplicates (need idempotency). gRPC (HTTP/2 + protobuf), Thrift, Finagle are modern RPC systems that are more honest about network semantics.

Message-Passing Dataflow

Producer sends a message to a named queue or topic; broker buffers it; consumer processes when ready. Advantages: producer doesn't need receiver's address; buffer absorbs spikes; fan-out to multiple consumers; retry on consumer crash. One-way (fire-and-forget). Actor model (Erlang OTP, Akka): concurrency + message passing within a process; distributed actor frameworks extend this across nodes.
