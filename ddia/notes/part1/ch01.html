Part I — Foundations

Chapter 1: Reliable, Scalable, and Maintainable Applications

The three non-functional pillars every data system must satisfy — and the trade-offs between them.

The three goals data systems must balance — not always simultaneously achievable.

§1.1

Reliability

A system is reliable if it continues to work correctly even when things go wrong. "Correctly" means performing the function the user expected, tolerating user mistakes, performing well enough under expected load, and preventing unauthorised access/abuse.

Fault
A component deviating from its specification.
Failure
The whole system stops providing the required service to the user.
Goal: build fault-tolerant systems that prevent faults from causing failures. Netflix Chaos Monkey deliberately introduces faults to test tolerance.

Types of Faults

Hardware Faults

Disk crashes, RAM errors, power outages, NIC failure. Mean time to failure for one disk: ~10–50 years. With 10,000 disks, expect ~1 failure/day. Solution: RAID, redundant power, hot-swappable CPUs. Cloud VMs fail more frequently and with less warning.

Software Errors

Systematic bugs triggered by unusual inputs, runaway processes consuming shared resources, cascading failures. Much harder to anticipate than hardware faults — correlated across nodes. No simple fix: careful thinking, testing, process isolation, monitoring, crash-and-restart.

Human Errors

Configuration errors by operators are the leading cause of outages. Mitigations: well-designed abstractions and APIs that minimize surface for errors; sandbox environments; thorough testing (unit through integration); quick rollback; detailed monitoring and alerting.

Fault tolerance converts faults into continued service rather than failures.

§1.2

Scalability

Scalability is the ability to cope with increased load. It's not a one-dimensional label — a system may handle 10× users easily but struggle with 10× data volume. Always define load parameters before asking "how does performance change as load grows?"

Describing Performance

Batch systems: care about throughput (records/second). Online systems: care about response time (from client's perspective, includes network + queueing + processing).

Use percentiles, not averages. Median (p50) = half of requests faster. p95/p99/p999 = tail latency — matters most for customers with most data (often premium customers). Even if only 1 in 1000 requests is slow, parallel fan-out means any request waiting for 100 calls will see the slow one. Head-of-line blocking: a slow request holds up all requests behind it in a queue.

Response time distribution. The long tail (p99/p999) hurts the most-engaged users and amplifies in fan-out scenarios.

Approaches to Scaling

Vertical scaling is simpler but hits physical/cost limits. Horizontal scaling (shared-nothing architecture) is more flexible.

§1.3

Maintainability

The majority of the cost of software is in ongoing maintenance — fixing bugs, adapting to new platforms, adding features. Three design principles:

PrincipleDefinitionHow to achieve
OperabilityMake it easy for operations teams to keep the system running smoothly.Good monitoring/observability; avoid single points of human knowledge; good default behavior; self-healing; predictable behavior.
SimplicityRemove accidental complexity (complexity not inherent to the problem). Make it easy for new engineers to understand the system.Good abstractions; hide irrelevant details; clean interfaces. Beware: a bad abstraction can make things worse than no abstraction.
EvolvabilityMake it easy to make changes: adapt to unanticipated use cases, new requirements, business changes.Agile practices, TDD, refactoring, loosely coupled design, simple architecture.
