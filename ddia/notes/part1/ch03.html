Chapter 3: Storage and Retrieval

How databases store data on disk and find it again — hash indexes, SSTables, B-trees, and the wide world of OLTP vs OLAP.

§3.1

Log-Structured Storage

The Simplest Database

An append-only log file. db_set k v appends a line; db_get k scans from the end. Write: O(1). Read: O(n). Real databases do better, but the append-only log is the foundation of many modern storage engines.

Hash Index

Keep an in-memory hash map: key → byte offset in the log file. On write, append record and update the map. On read, look up offset, seek to position, read record. This is essentially Bitcask (Riak's default storage). Works well when you have a large number of writes per key but a number of distinct keys small enough to fit the map in RAM. Range queries are not efficient.

Compaction: Log segments grow; periodically merge old segments, keeping only the most recent value per key. Merge can happen in a background thread. Tombstone records flag deleted keys.

SSTables and LSM-Trees

SSTable (Sorted String Table): like the log-structured segments above, but keys are sorted within each segment file. Benefits: (1) merging segments is efficient — mergesort, like in merge sort; (2) the in-memory index can be sparse (one pointer per every few KB rather than one per key); (3) records between known offsets can be grouped and compressed.

LSM-Tree (Log-Structured Merge-Tree): writes go to memtable; flushed to SSTables; compacted through levels. Reads check each level top-down.

§3.2

B-Trees

The most widely used indexing structure. Break the database into fixed-size pages (traditionally 4 KB, matching hardware page size) and read/write one page at a time. Each page contains sorted keys and references to child pages. Branching factor is typically several hundred keys per page.

B-Tree: 3-level example. Root → internal → leaf. WAL written before any page mutation for crash safety. Branching factor ~500 makes trees shallow.

§3.3

OLTP vs OLAP

OLTP vs OLAP: fundamentally different access patterns requiring different storage optimizations.

Star Schema (Data Warehousing)

Star schema: one central fact table (billions of rows, each an event/transaction) surrounded by dimension tables (descriptors/attributes).

Column-Oriented Storage

Row-oriented: all columns of a row stored together — good for OLTP (fetch one record quickly). Column-oriented: all values of one column stored together — good for OLAP (read only 2 of 100 columns → 50× less I/O). Column compression: bitmap encoding (one bit per row per distinct value for low-cardinality columns) + run-length encoding → often 10× compression. Vectorized processing: tight loops over column arrays, SIMD CPU instructions. Sort keys: sort by most-queried column (e.g., date). Multiple sort orders across replica copies.
